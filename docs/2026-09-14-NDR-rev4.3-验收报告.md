## 四、发现

### A（登记遗漏，非阻塞）
spec §1.3 要求把 G1 的**已知残留**"与 §4 一同登记"，但 README 技术债表里**没有对应行**。应补一行（纯登记）：
> handled 索引以 IMAP UID 为键；UID 不可得时绕开索引 → **unknown 类** NDR 每轮会重复告警一次（已匹配的因 `forward_log.bounced` 返回 `dup`，不重复告警）。彻底解 = 把键改为 **NDR 自身的 `Message-ID`**（表内 `message_id` 列已存在但恒写 `""`）。为什么现在不做：UID 取不到属罕见服务端异常；何时再做：若观测到 `bounce_uid_missing` 计数器持续增长。

### B（测试小瑕疵，非阻塞）
1. `test_g3_last_bounce_poll_ts_inf` 直接**读 `serve.py` 源码文本**断言 `'float("-inf")' in src` —— 属脆弱断言（改引号/换写法即挂）。其行为断言（`_bounce_poll_due(100.0, -inf) is True`）已足够，建议删掉源码文本检查或改为断言模块属性。
2. `test_g2_run_sweeper_two_rounds_throttled` 直接改 `serve_mod._shutdown_event` / `_last_bounce_poll_ts` 并在**函数末尾手动还原**；若断言中途失败则不会还原 → 全局态泄漏给后续用例（正是我们前几天在 `test_bounce.py` 修过的那类顺序依赖）。建议改用 `monkeypatch.setattr`。
3. README 技术债节末尾仍写"本节仅登记，**不加用例**"，但 G4 恰恰加了一条 characterization 用例 —— 文字与事实略冲突，建议改为"仅登记；G4 另附一条记录该限制的用例（不修功能）"。

### C（报告口径，非阻塞）
- 报告写"基线 329"，但 rev4.2 的基线是 **334**（337 = 334 − 1 移除 + 4 新增）。337 这个数没问题，**基线数字引错**。
- 改动表把 rev4.2 的 F1/F2/F3 与 rev4.3 的 G1–G4 混在一起列（累计口径而非本轮增量），容易让人误判本轮范围。
