## 二、观察①：`UID FETCH` 失败时静默 continue —— **修**

**位置**：`mailbots_next/core/ingest.py:436-440`

**为什么必须修**：这条违反本次重构的第一原则"**绝不静默跳过**"。现在的行为是"每 30 秒空转一次、日志里一点痕迹都没有"，**和 IDLE 空转是同一个病**：某封邮件若因服务端问题永远取不到 payload，会一直重扫、永远没人知道，直到某天有人发现"这封没被处理"。

**改法（两三行）**：`UID FETCH` 返回非 `OK`、或 `_extract_raw_from_fetch()` 得到空 `raw_bytes` 时：

1. **先 `_log.warning(...)`** —— 日志里必须含 `account` / `folder` / `uid`（便于定位是哪封）；
2. **再 `increment_counter("uid_fetch_empty")`**；
3. **然后才 `continue`**。

**保持现状的部分**：**不推进水位**（水位推进条件不变，仍然只在"成功"或"已入队"时推进）。本轮只要求"留痕"，不改语义。

## 三、观察②：`IDENTIFY_EXCEPTION` 分支缺幂等检查 —— **修**

**位置**：`mailbots_next/serve.py:93-99`（`_identify_type` 抛异常那条分支）

**为什么要修**：**对称性** —— 同一个 `process_email` 里其它入队分支（`UNCLASSIFIED` `:110-115`、`EXTRACT_EXCEPTION`、`EMPTY_ROWS`、行级 `ROW_EXCEPTION`）**都有** `has_pending_message(...)` / `has_pending_error(...)` 检查，唯独这一处没有。将来别人 refactor 时会问"为什么这里不一样"。后果是低危但真实的：同封邮件在多账号 / 多文件夹各处理一次时会**重复入队**，不影响转发正确性（转发侧有 dedup 兜着），但会污染 `error_queue`、干扰运维视线。

**改法（一行）**：入队前补上与 `UNCLASSIFIED` 分支**完全对称**的幂等检查：

```python
if not has_pending_message(message_id):
    add_error(message_id, "", "identify", "IDENTIFY_EXCEPTION", ...)
```
