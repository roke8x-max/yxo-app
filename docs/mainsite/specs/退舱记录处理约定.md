# 退舱记录处理约定

> **这是全项目最容易被误伤的一条业务规则。任何会「读到或写到订舱记录」的批量动作，动手前先读本文件。**
> 最后校订：2026-10-21（§7 代码侧落地现状全量复核；2026-10-08 毛骁洋修订 §3 铁律 1 与 §4 的删除规则：**人能删，系统不能替人删**）。

---

## 1. 为什么要单独一份

订舱记录会出现 `状态 = "退舱"` 的行，表示这票业务已退。**这条记录本身是业务凭据，要长期留存**——它不属于可清理的垃圾数据。

项目里已经因为误碰它踩过坑，所以把它从 `AGENTS.md` 拆出来，单独成文。

---

## 2. 触发场景

**舱单导入 / Excel 导入 / 手工改行 / 去重 / 清理 / 迁移 / 状态改写 / 按班列整理** —— 任何会读到或写到 `records` 表的批量动作。

---

## 3. 五条铁律

1. **禁止自动化 / 批量删除** —— 脚本、清理任务、批量整理（如按班列整理）一律**不得**删除退舱行，也不得清空它的字段。
   **人工手动删除是允许的**：由人主动发起、一条一条地删（软删或彻底删除都可以）——**系统不得替人做这个决定**。（2026-10-08 毛骁洋修订；原文为「永不删除」）
2. **永不作为「导入更新」的目标** —— 导入若命中退舱记录，**不得覆盖其任何字段**。
3. **永不与同客编的「正常」记录合并** —— 同一数字段同时存在「正常 + 退舱」是**合法留痕**，不是脏数据，别去重。
4. **任何涉及退舱记录的批量操作，动手前一律先问毛骁洋**，问清当次意图再执行。
5. **不要复用上一次的处理方式** —— 每次遇到都重新问。上一次允许删的，不代表这一次也能删。

---

## 4. 人也要能用（毛骁洋 2026-10-06 补充；2026-10-08 修订删除规则）

> **原话要点：不能静默自动处理；如果人工都不能处理，那也是个问题。**

所以铁律不是"把退舱记录封死"，而是**明确划定它能做什么、不能做什么**：

| 允许 | 不允许 |
|---|---|
| **复制**该行 | **自动化 / 批量删除**（脚本、清理任务、按班列整理等） |
| **修改「备注」** | 修改其他任何单元格 |
| **人工手动删除**该行（软删 / 彻底删除）—— 🔸 **2026-10-08 洋放宽**，见下方边界 | 作为**批量操作的落点**（例如按班列改发班时间） |
| 查看、筛选、导出、参与统计排除 | 系统在**无人确认**的情况下动它 |

**「人工手动删除」的边界（2026-10-08）**
- 指的是**人主动发起、一条一条地删** —— 网页上点删除、或手工执行一条针对某条记录的删除。
- **不包括**：脚本批量删、清理任务顺带删、按班列/按条件批量删、"上次这么处理过所以这次也这么处理"。
- 一句话：**人能删，系统不能替人删。**

**配套要求**
- **`sync_departure`（按班列批量改发班时间）必须排除退舱行** —— 这是当前唯一"必须改"的一条。
- **不得"静默自动处理"**：任何涉及退舱的批量动作，要么**排除**它，要么**明确报出来**；不许在用户不知情的情况下动它。

---

## 5. 做去重 / 清理前的强制自查

判断一条记录能不能清理，**不能只看箱号是否为空**，必须先看状态。至少要**同时**满足：

- 状态为空或「正常」（**非退舱**）
- 无箱号、无封号
- 无 `updated_by` / `updated_at`（从来没人维护过）

**只有这样的空壳才可能是误产生的重复。任何一条不满足，先问。**

## 8. 复测用的只读 SQL

```sql
SELECT COALESCE("状态",'(空)') AS 状态, COALESCE(is_deleted,0) AS 软删, COUNT(*)
  FROM records GROUP BY 1, 2;
```

> 生产库以只读为主；**不要**在生产库上跑任何写操作。需要查询时优先复制副本再用 `mode=ro` 打开。
