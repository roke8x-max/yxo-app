## 一、先回答洋的问题：口令和密码**机制上已经分开**

| 概念 | 代码里是什么 | 什么时候生效 |
|---|---|---|
| **口令**（系统识别用） | 环境变量 `YXO_AUTH_PASSWORD_<KEY>`（`auth/schema.py:93-98`） | **只在首次建库种子新用户时读一次**；用户已存在时种子语句跳过（`init_db`，`auth/schema.py:109-140`）。之后**不参与任何登录校验** |

① 影子期守卫（§2.1）；② 改密 / 重置密码 / 停用后**踢会话**（§2.2）。
**不新建认证逻辑、不改登录机制、不动权限矩阵。**

> ⚠️ 但有一条要知道：`init_db(strict=True)` **每次启动都会检查这 5 个 env 变量是否存在**（`auth/schema.py:117-124`），
> 缺了直接拒启动 —— 即使账号早就建好了、变量早已不参与登录。所以「口令」在生产**永远得留着**，删了服务起不来。

### 4.1 接口契约（请求体 / 返回 / 状态码，写死）

> 前端 `fetch` 走全局包装器（`static/app.js:14-23`），**CSRF 头自动加，不要手写**；后端两个 POST 都在门禁的 CSRF 层（`auth/__init__.py:96-98`）之下，缺头即 403。

**① `GET /api/admin/users`**
→ `200 {"ok": true, "users": [{id, username, role, scope_type, scope_companies, disabled, created_at}, ...]}`
（`scope_companies` 原样返回 JSON 字符串，由前端解析；**永不含 `pw_hash`**）

**② `POST /api/admin/users/reset_password`**
请求：`{ "username": "冯茜", "password": "可选" }`

| 情况 | 行为 |
|---|---|
| **`password` 字段不存在或为 `null`** | **后端生成随机密码**（规则见 §4.3-2），生成结果只在本次响应里返回 |
| **`password` 存在但为空串 `""`** | **400「新密码不能为空」** —— 空串一律视为非法输入，**不**当成"帮我生成"。理由：管理员手滑清空输入框，与"我要随机密码"是两件事，混在一起会让人拿到一个自己不知道的密码（ds 提，采纳） |
| `password` 有值 | 过 `password_strength()`，不过 → 400 + 具体 msg |
| `password` 是**非字符串**（如数字 `123`） | **400「新密码格式错误」**（不要报成"不能为空"，那是另一回事） |
| 成功 | `200 {"ok": true, "username": ..., "self": <bool>, "password": "<仅随机生成时才有>"}`；**输入型不回传 `password`** |
| 用户不存在 | 404 |
| 目标是自己 | 允许（等价于改密），踢会话，响应带 **`"self": true`** —— 前端据此走「提示 + 弹登录层」，别让管理员干等到点下一个 tab 才被 401 踢掉 |

> 前端「生成随机密码」按钮**必须显式不传 `password` 字段**（不是传空串）。

> **随机密码一律后端生成**，前端只负责显示 + 复制按钮 —— 强度规则只存在 `service.password_strength()` 一处，前端不复制规则（避免两张表漂移）。

**③ `POST /api/admin/users/set_disabled`**
请求：`{ "username": "冯茜", "disabled": 0 | 1 }`
→ 成功 `200 {"ok": true, "username": ..., "disabled": <0|1>}`
→ **停用自己 → 403**「不能停用自己的账号」；用户不存在 → 404。

**`disabled` 归一化写死**（别只处理 int）：
`1 / True / "1" / "true"`（大小写不敏感）→ `1`；`0 / False / "0" / "false"` → `0`；**其他一律 400「disabled 只能是 0 或 1」**。

**④ `POST /api/change_password`（已有，本次加两处）**
请求：`{ "old_password": ..., "new_password": ... }`（不变）
新增：首行影子期守卫（403）；成功分支补 `dao.delete_user_sessions(username)`。

### 4.2 前端交互补充（防手滑）

- **输入型重置密码**：弹窗要「新密码 + 确认新密码」两栏（前端比对一致）+ 二次确认「确认重置「冯茜」的密码？该用户所有在线会话会立即失效」。理由：管理员手输打错一个字 = 把别人密码改成自己都不知道的串。
- **随机生成型**：只显示一次 + 「复制」按钮，关闭弹窗后不可再取。
- 操作完成后刷新列表（`disabled` / 状态列要跟着变）。
- **停用自己**：当前用户那一行的「停用」按钮直接 `disabled`（比只靠后端 403 友好）。
- **`scope_companies` 解析**：先判 `null` / `""` / 解析异常 → 显示「—」，**不要直接 `JSON.parse(null)`**（会抛错把整表渲染打挂）。
- **重置的是自己**（响应 `self: true`）→ 走与改密成功同一套收尾：提示 + 清待提交队列 + 弹登录层。
- **改密成功后**：`_pending = {}` 清空待提交队列（变量名已核实：`static/app.js:1222`；否则 `beforeunload` 会拿已失效的会话把残留编辑再发一遍），然后 `showLoginModal("密码已修改，请用新密码重新登录")`。

### 4.3 两段参考实现（别只靠重试）

**1）随机密码生成**（`auth/routes.py` 或 `auth/service.py` 内私有函数）：

```python
import secrets, string

def _gen_password(length=14):
    """生成满足 password_strength 的随机密码：先放各类别各 1 个，再补随机，最后打乱。"""
    upper = string.ascii_uppercase
    lower = string.ascii_lowercase
    digits = string.digits
    pool = upper + lower + digits
    while True:                      # 理论上 1 次即出，保险起见设上限
        chars = [secrets.choice(upper), secrets.choice(lower), secrets.choice(digits)]
        chars += [secrets.choice(pool) for _ in range(max(0, length - 3))]
        secrets.SystemRandom().shuffle(chars)
        pw = "".join(chars)
        ok, _ = service.password_strength(pw)
        if ok:
            return pw
```

> 关键点：**先把三类字符各塞一个再打乱**，不要"纯随机 12 位然后祈祷它合规"——
> 后者在审查时会被问"重试也失败怎么办"，而且概率上确实存在（虽极小）。

**2）`disabled` 归一化**：

```python
def _to_bool01(v):
    if isinstance(v, bool):
        return 1 if v else 0
    if isinstance(v, int) and v in (0, 1):
        return v
    if isinstance(v, str) and v.strip().lower() in ("0", "1", "true", "false"):
        return 1 if v.strip().lower() in ("1", "true") else 0
    return None      # 调用方据此返回 400
```

## 十、待洋拍板（4 条，不拍板先按"不做/按建议"处理）

**Q1 改密后连「自己」的会话也踢掉，可以吗？**
删 `delete_user_sessions(username)` 是"踢掉该用户全部会话"，**包括刚改密这台**。后果：改完密码得重新登录一次。
建议：**就全踢**（最安全、实现最简单，前端弹登录层引导重登）。
提示文案要写清是「**密码已修改，请用新密码重新登录**」——别让用户以为改密失败（ds 提醒）。
若你嫌烦，可以改成"只踢其他会话、保留当前"——但那要区分当前 sid，复杂度明显上升，我不推荐。

**Q2 需求 C（首次登录强制改初始密码）做不做？**
要做就得给 `auth_users` 加 `must_change_pw` 列 + 迁移 + 登录返回字段 + 前端强制跳转。
建议：**本期不做**。理由：生产 5 个人、口令是你亲自发下去的，且翻 1 前还要试跑；等真出"初始密码被人用过"的问题再说。**这条要你点头才动 schema。**

**Q3 后台要不要能改「数据范围」（scope）？**
工单标可选。建议：**不做**。改 scope 直接决定谁能看哪几家公司，属于"权限变更"，误点后果比改密码严重；真需要时手工改库更稳妥。

**Q4 验收 B9 的口径：冯茜等人在后台应该看到什么？**
现在 `enterAdmin` 对无 `config:manage` 也无 `price:manage` 的人是「整页提示无权访问」；冯茜有 `price:apply` 但**没有** `price:manage`/`config:manage` → 她现在进后台看到的就是「无权访问」。
建议：**保持现状**（本次不动他们的后台可见性），只确保「用户管理」tab 只对 `user:manage` 出现。
