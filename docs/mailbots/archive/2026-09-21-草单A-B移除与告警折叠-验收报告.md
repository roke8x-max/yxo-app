## 7. 发现的问题

### 7.1 🔴 代码层：突发结束后，"共 N 次"汇总会一直不发（**属我 spec 的设计缺陷**）

`_flush_expired_windows()` 被放在 `notify()` 的**早退之后** —— 也就是**只有 `program_error` 到来时才会去补发过期汇总**。实测（我的探针场景 3）：

```
10 条同类 → 发 1 条；时钟 +61s；来一条 forwarded ⇒ 发送次数仍为 1，state 还留着
⇒ 只有下一条 program_error 到来时，才会补发"共 10 次"
```

**后果**：突发结束后（真实事故就是"7 秒 8 条然后没了"），"共 N 次"要等到**下一次程序错误**才出现——可能是几天后，而那时文案里的"最近 60 秒"已经失真。**首条始终立即发出 ⇒ 不会漏告警**，所以这条**不影响安全性**，但削弱了折叠最有价值的那一半信息。

**建议改法（1–2 行）**：把 `_flush_expired_windows()` 提到那个早退**之前**（它对非折叠类型也安全、不建 state、无递归），并把汇总文案里的"最近 N 秒"去掉（改成"该批"），避免迟到时失真。
> ⚠️ 这是我 spec 伪代码写错的位置（我把它放在了早退之后），实现是**忠实照做**的 ⇒ **不算交付方的问题**。

### 7.2 🟡 交付方用例 11（state 上界）是**空测试**

```python
n.send_program_error(OPS_OWNER_EMAIL, f"e{i}", f"unique detail number {i} xyz")
```
detail 之间**只差数字** ⇒ 归一化后**全成同一个指纹** ⇒ state 恒为 1 ⇒ `assert len(state) <= 500` **永远成立**。
**我实测**：把 `_COLLAPSE_MAX_ENTRIES` 改成 `500000` 后该用例**照样通过** ⇒ 它拦不住"上界被删掉"。
（功能本身没问题：我用**字母区分**的探针验证上界确实工作 = 500 条、无异常。）
**改法**：把 detail 改成字母区分（如 `f"kind-{chr(97+i%26)}…"`），或直接断言"塞 600 个真不同指纹后 == 500"。
