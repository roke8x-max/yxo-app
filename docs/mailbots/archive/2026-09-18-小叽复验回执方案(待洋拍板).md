### 🔴 没守住的路径 ①：`import_excel.py`（网页端「导入 Excel」，现行入口）

```python

exist = conn.execute('SELECT id FROM records WHERE "客户编码"=?', (key,)).fetchone() if key else None
```

- **无 `状态<>'退舱'` 过滤** ⇒ 若压进来的 Excel 命中一条退舱记录的客户编码，**直接覆盖其字段** = 违反铁律 2；
- **也无 `is_deleted=0` 过滤** ⇒ 连**软删记录**都会被更新覆盖（附带隐患：导入会"复活"软删行，而网页端本来把"恢复"做成一个显式按钮）；

- **风险已实测存在**：`CQWLJT260923001-D` 有两条记录**客户编码是完全相同的字符串**（id1827 正常 / id2433 退舱，箱号都为空）。`fetchone()` 没有 `ORDER BY`，当前 SQLite 恰好返回 id 较小的 id1827（**正常**那条）⇒ 侥幸没踩到，**但这是未定义顺序，不是设计保证**；
- **与 `manifest_engine` 口径不一致**：同一个"导入更新"概念，两套实现，一套管、一套不管 —— 属**同一类病**。

**我建议修**（改动 3 行：SQL 加 `AND COALESCE("状态",'')<>'退舱'`）。理由：它是**无人工介入的批量入口**，一旦命中就是**静默覆盖**（`import_excel` 不写 `update_log`，事后无法察觉），而修法与风险都极小。
⚠️ **但有一个要你拍板的副作用**：要不要**同时**加 `AND COALESCE(is_deleted,0)=0`？
- 只加退舱过滤（保守）：软删记录的行为完全不变，导入仍会"复活"它；
- 两个都加（彻底）：导入**不再复活软删记录**，而是**新增一行** ⇒ 可能出现"同客户编码两行"。这是**行为变更**，得你点头。
（我的倾向：两个都加——因为"软删"在网页端是个有按钮的显式动作，导入顺手复活它才是意外行为。但这确实会改变同事看到的结果。）
