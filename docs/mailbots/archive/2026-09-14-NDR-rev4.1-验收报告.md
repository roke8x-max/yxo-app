## 五、芙蕾雅复核新发现

### A（P1，覆盖性回归 —— **主要责任在我的 spec 表述**）
`_candidate_seqnos`（bounce.py:272-281）把 `SEARCH UNSEEN HEADER Content-Type "delivery-status"` 作为**主路径**，仅在 search 抛错/非 OK 时才回退 `UNSEEN`。

问题：RFC 3501 §6.4.4 的 `HEADER <field> <string>` **只匹配消息的顶层信头**；MIME 部件的信头属于正文，不参与匹配。于是：
- 主流 NDR（顶层 `Content-Type: multipart/report; report-type=delivery-status`）→ 命中 ✅
- **非标准形态 NDR（顶层是 `multipart/mixed`、`message/delivery-status` 嵌在正文里）→ 该搜索匹配不到，而因为 search 返回 OK，也不会回退 → 这封 NDR 从头到尾不会被看到** ❌

而 rev4 原本扫全量 `UNSEEN`，是能抓到的 → **这是覆盖性回退**，恰好落在"绝不能漏退信"的初衷上。

**修正建议**：把"全量 `UNSEEN` + 头部预筛"作为**基线**（预筛已保证不下载全文，成本很低），HEADER 定向搜索只作**可选叠加**（取并集），**不得替代**。
> 自我认领：这条路径是我在 rev4.1 spec §4 里给的（"先 HEADER 定向搜索…不支持再回退"）——我只考虑了"服务端不支持"，没考虑"服务端支持但匹配不全"，导致了这个洞。

### B（P2，低成本加固）
`_NDR_SUBJECT_KWS`（:37-40）只有英文关键词。建议补中文：`退信 / 无法投递 / 未送达 / 投递失败 / 邮件退回 / 退信通知`。虽然 `"report" in tl` 已覆盖多数情况，但补上几乎零成本，能直接缩小 §四 里自报的残留缺口。
