## 2. 【P0】`RFC822` fetch 会隐式置 `\Seen`，必须改 `BODY.PEEK`

### 2.1 事实

RFC 3501 §6.4.5 明确规定：`RFC822` **等价于** `BODY[]`，而 `BODY[]` 会**隐式设置 `\Seen` 标志**。

现状 `core/bounce.py:200`：
```python
_, raw = conn.fetch(num, "(RFC822)")     # ← 等价 BODY[]，隐式置 \Seen
```
后果：轮询时**每一封被扫到的未读邮件都会被标成已读**——不只是 NDR，同事收件箱里的**正常邮件也会被吃掉未读角标**。这与 rev4 意图（及洋的 D1：不吃未读角标）**直接冲突**；也就是说，靠"跳过时不调 `store()`"来实现"不标 Seen"是**无效**的，因为标志在 `fetch` 时就已置位。

### 2.2 要求（必做）

1. `poll_bounces` 内**所有**取信一律改用 PEEK：
   - 只看头：`conn.fetch(num, "(BODY.PEEK[HEADER])")`
   - 取全文：`conn.fetch(num, "(BODY.PEEK[])")`
2. **删除 `core/bounce.py` 中全部 `conn.store(..., "+FLAGS", "\\Seen")`**（现有 3 处：:140 / :166 / :212）。
3. 验收断言（可 grep）：
   - `grep -n 'Seen' mailbots_next/core/bounce.py` → **0 条**
   - `grep -n '"(RFC822)"' mailbots_next/core/bounce.py` → **0 条**

> `BODY.PEEK` 是唯一能**保证**不置 `\Seen` 的取信方式；即便某些服务端对 `RFC822` 不置位，也应一律用 PEEK，不依赖服务端脾气。

### 2.3 同时要实测的（写进部署验证手册）

`core/ingest.py` 的 Idler（:277）与 `fetch_raw_by_uid`（:365）**也在用 `(RFC822)`**。若该服务端确实会置位，则业务文件夹的邮件会被静默标已读，`MarkSeenBatcher` 那套设计**形同虚设**。

**本 spec 只要求改 `poll_bounces`**；Idler 是否一并改 PEEK，由洋拍板（见 §10）。但必须先在部署验证手册里补一个实测步骤：

```python
# 探测：RFC822 取信是否会把邮件标成已读
# 取一封未读邮件的 uid，记录其 FLAGS → 用 RFC822 取一次 → 再查 FLAGS
typ, d = conn.fetch(uid, "(FLAGS)")
print("before:", d)
conn.fetch(uid, "(RFC822)")
typ, d = conn.fetch(uid, "(FLAGS)")
print("after :", d)      # 若出现 \Seen → 服务端确认置位
```
结论（置位与否）回给芙蕾雅，用于决定 Idler 是否也要改。

## 3. 【D1】本地 handled 索引（替代 `\Seen`）

1. **新表**（建在与 `forward_log` 同一连接/库上，`core/store.py`）：
   ```sql
   CREATE TABLE IF NOT EXISTS bounce_handled (
       account TEXT NOT NULL, uid INTEGER NOT NULL,
       message_id TEXT, forward_id TEXT, outcome TEXT,
       handled_at TEXT NOT NULL,
       PRIMARY KEY (account, uid)
   )
   ```
2. `poll_bounces` 扫描到一封**已判定为 NDR** 的邮件时：
   - 先按 `(account, uid)` 查 `bounce_handled`；**已存在 → 直接跳过**（不重复入队、不重复告警）。
   - 处理完（不论 `requeued` / `unknown` / `already-bounced` / `delayed 忽略`）→ **写入一条** `bounce_handled`。
3. **任何地方都不得再写 `\Seen`**（见 §2）。
4. 未决 `\Seen` 的取舍已定：**NDR 也保持未读**（同事应看到自己的邮件被退）。随之而来的是"同一封 NDR 每轮都会被扫到"——靠 §4 的 header 预筛 + 本索引把成本压到可接受。
5. **清理**：`bounce_handled` 按 `handled_at` 定期清理（建议 90 天）。可复用 sweep 低频执行（如每天一次），或先在 §9 登记为债——**由 OpenCode 选一种并在报告中说明**。

> 注意：`(account, uid)` 以 IMAP UID 为键；若邮箱文件夹被重建（UIDVALIDITY 变化），旧记录会失效但**只会导致重复处理一次**，无正确性风险。

## 4. 【P1-1】降低轮询负载（**前提：不得漏 NDR**）

现状：`search(UNSEEN)` 后对**每封未读**做全文 `fetch`；又因 §3 不再标 `\Seen`，未读集合**永不缩小** → 每轮把 4 个收件箱的全部未读邮件全文下载一遍。同事未读几百封时负载可观。

**改为两段式：**

1. **第一段（近零成本）**：`conn.search(None, 'UNSEEN HEADER Content-Type "delivery-status"')`
   —— 主流 NDR（`multipart/report; report-type=delivery-status`）会在此直接命中。
   - 若服务端不支持 `HEADER` 搜索（报错/异常）→ **回退**到 `search(None, "UNSEEN")` 走第二段全量预筛。
2. **第二段（预筛，fail-open）**：对候选 uid 先取 `(BODY.PEEK[HEADER])`，用宽松预判决定是否取全文：
   ```python
   def _looks_like_ndr_headers(hdr_text: str) -> bool:
       # 宽松 OR，任一命中即取全文（宁可多取，不可漏）
       # ① Content-Type 含 report / delivery-status
       # ② Subject 命中关键词：退信 / 无法投递 / 未送达 / Undeliverable /
       #    Delivery Status / Delivery Failure / Mail delivery failed / Returned mail
       # ③ From 含 MAILER-DAEMON / postmaster / mailer-daemon
       # ④ 含 Auto-Submitted: auto-replied / auto-generated
   ```
   **铁律：预判必须 fail-open。** 只要没把握，就取全文判。本功能的初衷就是"绝不漏退信"，**性能优化不得以漏判为代价**。
3. 取到全文后再走既有 `is_ndr` 严格判定（§5）。
4. 可选：新增 `BOUNCE_LOOKBACK_DAYS`（默认 30），给第二段兜底扫描加 `SINCE` 边界，限定总量。

## 5. 【P1-2】收紧 `is_ndr` 判据 (c)

现状判据 (c)：某个 `text/plain`（或 `message/delivery-status`）正文里存在以 `Action:` 开头的行即判 NDR。
→ 同事正常邮件（如会议纪要含一行 `Action: 请跟进`）会被**误判为 NDR**：拿不到 fid、次键候选为 0 → 走 `unknown` 分支 → **既发一条误告警，又消费掉该邮件**（配合 §3 会记进 handled 索引）。

**改法**：(c) 需**同时**满足两条才成立 ——
- 存在 `Action:` 行；**且**
- 存在 `Final-Recipient:` 或 `Diagnostic-Code:` 行。

（判据 (a) 存在 `message/delivery-status` 部件、(b) 顶层 `multipart/report` + `report-type=delivery-status` 保持不变。）

## 6. 【P2-1】`row_key` 公式去掉重复定义（本次 bug 根因）

现状 `core/act.py::_serve_row_key` 把 `serve.py` 的行键公式**复制**了一份——而 rev4 修掉的那个 v3 真 bug（重放恒 duplicate、条目永不 resolve），根因正是"两处公式各写各的"。

**改法**：
1. 在**中性位置**新建唯一实现 `mailbots_next/core/rowkey.py::serve_row_key(row) -> str`（放 `core/` 下，`serve.py` 与 `core/act.py` 都从它导入，**避免 serve↔act 循环导入**）。
2. `serve.py` 计算 `row_key` 处（`_process_row` 内）改为调用它。
3. `core/act.py` 删除自带的 `_serve_row_key`，改从 `core.rowkey` 导入。
4. `_record_forward` 取值顺序：优先 `send_ctx` 里的 `_row_key`（`serve` 侧注入，单一来源），缺失时才用 `serve_row_key(row)` 兜底——**兜底也只调那一处函数**。

## 7. 【P2-2】测试补强（`mailbots_next/tests/`）

1. **e2e Step2 增补显式断言**：`row["row_key"] == f"0:{BOX}"`（现在只有 Step5 隐式覆盖）。
2. **新增：轮询不碰已读标志**——mock IMAP 记录所有调用，断言
   - `conn.store` **从未被调用**；
   - 取信用的 data item 是 `BODY.PEEK[HEADER]` / `BODY.PEEK[]`，**不含 `RFC822`**。
3. **新增：非 NDR 邮件**（正常客户邮件）→ 不 `store`、不告警、计入 `skipped_non_ndr`。
4. **新增：header 预筛 fail-open** —— 头部形态模糊的邮件仍会取全文并进入判定（不得被静默丢弃）。
5. **新增：`is_ndr` (c) 收紧** —— 含 `Action:` 但没有 `Final-Recipient:`/`Diagnostic-Code:` 的正常邮件判 **False**。
6. **新增：handled 索引幂等** —— 同一封 NDR（同 account/uid）二次轮询：不重复入队、**不重复告警**。
7. 既有 16 个 rev4 用例（`test_bounce_rev4.py` 12 + `test_bounce_e2e.py` 4）必须继续全过；若因 PEEK/索引调整需微调 mock，属允许范围，但**不得删除既有断言**。
