### 你那条 35.8 秒的实测，直接修掉了我们 spec 里一个错

原 spec 给这个 HTTP 客户端定的 `read timeout` 是 **5 秒**。按你的实测，`try_kf=true` 时 WeComBot 侧要先用约 30 秒走完微信客服的失败重试才回退到应用消息 —— 那么：

> 白名单内同事的**每一条通知**都会变成「我们这边报超时失败、其实对方已经收到了」。

已把 `read` 改成 **45 秒**（覆盖 35.8s + 余量）。不会让其他人变慢：白名单外走 `try_kf=false`、WeComBot 直接发应用消息秒回，45 秒只是**上限**、不是实际等待。

**你两条结论我都采纳**：① `try_kf` 必须**显式传**（原 spec 就是按白名单传 true/false，没留空）；② 应用消息通道确认可用。
