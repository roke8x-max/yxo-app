## 1. 这次发生了什么（大白话）

停旧起新的验证过程中，企微收到大量这类通知：

```
❌ 程序错误 [error_id=xxxxxxxx]
Draft nums DB read failed: OperationalError: no such table: forwarded_drafts
```

**原因**：草单要分两类 —— "新草单"和"更新草单"；判"更新"的判据是去查一张**已转发草单台账**表。而这张表**从来没被建过**（也没有任何地方往里写过）⇒ **每封草单**都会报一次"表不存在"⇒ 一封草单一条告警，于是刷屏。

**性质与影响**：

- 这是**代码缺陷**，不是环境问题、不是配置问题；
- **不影响邮件转发**（客户照常收到邮件），也不影响写库；
- 受影响的是**通知**：真正的告警会被这堆重复信息淹没。

## 2. 本轮改了什么

### 2.1 移除"更新草单"判定与那张台账（根治）

草单不再去查台账，**一律按"新草单"处理**。这样报错的源头直接消失（不是"让它别报错"，是"不再做这件做不到的事"）。

为什么这样是对的：**机器人看不到人工转发**（它不监控任何「已发送」文件夹），所以它**无法可靠判断**"这封是不是更新版"——只看自己的记录，会得出错误结论。既定方向是 **宁可漏标，绝不误标**；"一律按新草单"正好就是"绝不误标"的状态。

> 将来若确实要做"更新/作废"，需要单独立项（要解决"内容是否真的变了"和"人工转发可见性"两件事），不是顺手能做的。

### 2.2 告警折叠（防同类错误刷屏）

- 同一类**程序错误**在 **60 秒**内只发**第一条**；
- 窗口结束时补发一条"（同类型错误最近 60 秒共发生 N 次，已折叠 N-1 条）"；
- **不同类型的错误不会被合并**（不会把两个问题混成一条）；
- **报警/待办类通知不折叠**（每条对应不同业务对象）；
- **日志仍然逐条记录、计数不变** —— 折叠只减少"发到企微的条数"，可追溯性不打折。

### 2.3 两道守卫（防同类问题复发）

- **表引用守卫**：代码里读/写的每一张表，必须要么在代码里有建表语句、要么能指明由谁建（例：`records` 由网页端建）——否则测试直接失败；
- **全新初始化冒烟**：在一个**空目录**里按真实启动路径初始化，断言"代码会读的每张表都真的存在"。

> 之前"代码读一张没人建的表"没被测出来，是因为**测试自己把那张表建了出来**，把缺陷盖住了。这两道守卫就是冲着这个盲区去的。

## 3. 你需要做的

### 3.1 现在（本轮代码合并前）：**基本不用做任何事**

- 旧系统照常运行，**不要起新服务**（避免新旧同时转发）；
- 网页端不动。

**可以提前做、不用等的只有一件**：把 `mailbots_next\secrets.json` 配好（见 §3.2 的 **A0**）。它只是本机上的一个配置文件，与代码是否合并无关；提前配好可以让部署那天少一个变量。

### 3.2 本轮合并后：按下面 4 步走

| 步 | 做什么 | 期望看到什么 |
|---|---|---|
| **A0** | **部署前先确认 `mailbots_next\secrets.json` 已配好**（可在拉代码前就做，它只是本机文件）：4 个邮箱密码（`ACCOUNTS`）+ 企微通知两项 `WECOM_NOTIFY_URL` / `WECOM_NOTIFY_TOKEN`（值与我们在用的那个 token 一致）+ `WECOM_KF_EMAILS` **留空** | 文件存在且键齐全。⚠️ **`WECOM_KF_EMAILS` 留空 = 所有人走应用消息、秒发**（实测 0.5 秒；若走微信客服通道要等约 35 秒才回退）<br>⚠️ 缺 `WECOM_NOTIFY_URL` / `WECOM_NOTIFY_TOKEN` 时**不会崩、也不影响邮件转发**，但企微通知会**发不出去**——日志会出现这条（**这是它的正常告警，不是新 bug**）：`WeCom client not available (WeComConfigMissing), notifications will loud-fail with notify_failed counter` |
| **A** | 拉最新代码：`D:\YXO_DATA\yxo_app` 里 `git pull`（生产只拉 `main`） | 拉取成功、无冲突（该目录当前干净，HEAD 已是最新 `main`） |
| **B** | 按执行清单 **§6** 跑**一轮**自检：`.\venv\Scripts\python.exe -m mailbots_next.serve --once` | **正常退出**、无 `Traceback`。（`--once` 现在真的"扫一轮就退出"，**也不会把邮件标为已读**） |
| **C** | 按执行清单 **§8** 逐条自检，**特别看新增的 [7]** | **[7]「程序错误」类告警 = 0 条**（这一项就是本次要盯的） |
| **D** | 确认后再走"停旧 → 起新"，并按 **§9** 做端到端验收 | 见执行清单 §9 |

⚠️ **B/C 两步不要跳**：这次的问题正是被"跑一轮再看日志"逼出来的 —— 这一步很有效，现在它已经是显式步骤。
⚠️ `--once` 的退出码 0 **只代表"这一轮跑完了"，不代表 SMTP 真的发出去了**；发信要按 §9 验收。
💡 `secrets.json` 是 **gitignored** 的、不进仓库；它有**进程内缓存** ⇒ **改完必须重启 `mailbots_next` 才生效**（改完不重启会以为"配了没用"）。

## 4. 配置与环境变量的变化

| 项 | 变化 | 你要做什么 |
|---|---|---|
| `NOTIFY_COLLAPSE_WINDOW_SEC` | **新增（可选）**，折叠窗口秒数，**默认 60**；设 `0` = 关闭折叠 | **不用设**。想临时关闭折叠时才设 `0` |
| `DRAFT_NUMS_DB_PATH` | **不再被读取**（台账功能已移除） | 若曾设过，**可以移除**（留着也无害） |
| `mailbots_next\data\draft_nums.db` | **不再被读取**（本地那个是 0 字节空文件） | 部署后**可以删掉**（可选，不影响运行） |
| `mailbots_next\secrets.json` | **需要补齐企微通知两项**：`WECOM_NOTIFY_URL`、`WECOM_NOTIFY_TOKEN`（**代码已在 main**，C 组那批） | 见 §3.2 的 **A0**。这个文件 gitignored、不进仓库；**有进程内缓存 ⇒ 改完要重启才生效** |

> 其余环境变量（`YXO_DB_PATH` / `FORWARD_SINCE` 必设、`BOUNCE_MONITOR_ENABLED` 必不设）**全部不变**，见执行清单 §2。
>
> 💡 另外两个**可选**：`NOTIFY_COLLAPSE_WINDOW_SEC` 与 `secrets.json` 的键都支持**同名环境变量覆盖**（环境变量优先）；用哪种都行，选一种别两处都写（否则以后改一处不生效、容易误判）。
