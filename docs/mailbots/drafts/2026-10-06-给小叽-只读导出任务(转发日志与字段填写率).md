## 1. 为什么需要这两样（读一遍，避免执行时跑偏）

### 1.1 转发日志的用途

新邮件机器人 `mailbots_next/` 已经写完但**从未上生产**（生产仍跑旧 `mailbots/`）。洋要做的不是"直接切"，而是**离线回放验收**：

> 拿仓库里已有的**真实邮件样本**喂给新系统（**只判定、不发送**），把它的判定结果与**旧系统实际转发了什么**逐条对照。

- **样本在本机**（仓库 `mailbots/tests/fixtures/real_imap_samples/`），不需要你提供。
- **"旧系统实际转发了什么"只有你那边有** —— 就是 `forward_log.db`。
- ⚠️ **不需要、也不允许在服务器上跑新系统**：新系统会连真实邮箱、会标已读、会写自己的库，在生产机上跑会干扰正在运行的旧系统。回放全部在**本机隔离环境**完成。

### 1.2 字段填写率的用途

洋 2026-10-06 的原话（大意）：**"有的同事会去做入站、入堆场、草单、报放单的状态，有的人就不会（其实我也不会），所以这些东西都没办法做自动化的设计。"**

也就是说：**同一批字段，不同同事的维护习惯不同**。任何依赖"没人稳定维护的字段"的自动化（待跟进提醒、看板、报表、告警）都会失真 —— 这很可能正是"很多功能没人用"的系统性原因。

⇒ 先用数据把这件事量出来，再决定哪些字段能做自动化。

## 2. 任务 A · 导出转发日志

### 2.1 位置与结构

- 库文件：`D:\YXO_DATA\yxo_app\mailbots\data\forward_log.db`
  （定义见仓库 `mailbots/forward_log.py:19-21`）
- 表 `forward_log`（DDL 见 `mailbots/forward_log.py:23-41`）：

  | 列 | 含义 |
  |---|---|
  | `id` | 主键 |
  | `robot` | DSK / ATB / 草单 / 运单号 |
  | `day` | `YYYY-MM-DD` |
  | `ts` | `YYYY-MM-DD HH:MM:SS` |
  | `owner` | 负责同事真实姓名 |
  | `company` | 公司 |
  | `code` | 客户编码 |
  | `box` | 箱号 |
  | `subject` | 邮件主题 |
  | `to_list` | **实际收件人**（对照的关键列） |
  | `sender` | 发信邮箱 |
  | `note` | 备注 |
  | `test` | 是否测试记录（0/1） |

### 2.2 要导出什么

- **范围**：`day` 在 **2026-07-25 ~ 2026-08-28**（样本覆盖 7/27~8/24，两端各留余量）。
- **全列导出，一列不落** —— 尤其 `to_list`、`robot`、`box`、`code`、`test`。
- **`test=1` 的记录必须一并导出，不要过滤**，只需保留 `test` 列。理由：过滤掉会让对照出现"凭空多出/少掉"的假差异。
- **格式**：CSV（UTF-8 with BOM，便于 Excel 打开）或 JSONL，二选一。
- **附带一行统计**：总行数、`day` 的最小/最大值、按 `robot` 分组的行数、`test=1` 的行数。

### 2.3 ⚠️ 一个必须知道的前提（会影响对照结论）

`mailbots/forward_log.py:11-12` 明确写着：本模块**"绝不能因为记日志失败而影响转发主流程 —— 所有调用点都用 try/except 包住，本模块内部也全程吞异常"**。

⇒ **`forward_log` 是"尽力而为"的记录，它自己也可能漏记。** 所以它**不能当作 100% 的转发真值**。

请在你导出的统计里**如实说明这一点**，本机侧做对照时会把差异标成"**疑似差异、需人工核**"，而不是直接判成新系统的错。

### 2.4 只读要求

- **优先做法**：先把 `forward_log.db`（连同 `-wal`/`-shm`，若存在）**复制到临时目录**，再对副本查询 —— 完全不碰生产文件。
- 若直接查，必须用只读方式（如 `file:...?mode=ro`）。
- **不要**在这个库上执行任何写操作、不要 `VACUUM`、不要建表建索引（`forward_log.py:46` 会在连接时 `executescript(DDL)`，所以**不要 import 这个模块去查库**，直接用 sqlite 只读打开）。

## 3. 任务 B · `records` 字段填写率统计

### 3.1 位置

- 生产主库：`D:\YXO_DATA\yxo_app\data\yxo.db`，表 `records`。
- **同样要求只读**（复制副本再查，或用 `mode=ro`）。

### 3.2 统计口径

- **只统计有效记录**：`WHERE COALESCE(is_deleted,0)=0`。
- **字段清单不要手写死**：请从仓库 `config.py` 的 `FIELD_DEFS`（`config.py:43-84`）读取，这样口径与系统一致、以后也不会漂移。
- **"空"的判定**：`NULL` 或 去空格后为空字符串，都算空。

### 3.3 要产出三张表

**表 1 · 全库字段填写率**

| 字段 | 类型(kind) | 总行数 | 非空行数 | 非空率 |
|---|---|---|---|---|

按"非空率"从低到高排序（**最需要看清的是"填得最少"的那些字段**）。

**表 2 · 字段 × 负责公司**（只列 `kind != "base"` 的操作字段）

| 字段 | 太平洋 | 港九港铁 | 东盟 | 同程配 | 中欧木业 | 沙坪坝 | 保时达 | 联运 |
|---|---|---|---|---|---|---|---|---|

填**非空率**（百分比）。分组用的是 `records."开票子公司名称"`（即"负责公司"，`config.py:71-72`）。
> 这张表要回答的正是洋那句"**有的人会填、有的人不填**"——用数据看是谁、在填什么。

**表 3 · 「待跟进」三字段的联合情况**

`config.py:97-98` 定义 `FOLLOWUP_FIELDS = ["状态", "草单", "报放单"]`，但前端 `static/app.js:452` 的注释说口径是「**仅看报放单**」。两张口径不一致（本机侧已登记，核实前不会动任何一边）。

请输出这三个字段的**联合分布计数**：

| 状态空? | 草单空? | 报放单空? | 行数 |
|---|---|---|---|

（8 种组合的计数即可，例如"三者都非空 / 仅报放单为空 / …"）

**这张表能直接判定哪个口径才是对的**：如果"状态"和"草单"的填写率很低，那前端"仅看报放单"就是符合现实的，`config.py` 里那三字段的配置就是过时的。
