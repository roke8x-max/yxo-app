## 2. 三处要修正/补充的地方

### 2.1 「仅通知文案」要写成「仅**企微通知**文案」，并补上历史背景

小叽说"A 与 B 的差别仅通知文案"——**对新系统成立**，但容易被误读。补两段背景：

- **旧系统里 A/B 是有"客户可见效果"的**：转发给客户的**邮件主题加前缀** `【草单更新】`（`mailbots/Draft_Forward_Robot.py:772`）、正文顶部加提示"此为更新版草单，此前版本作废"（`mailbots/draft_pending.py:228`）、并触发台账刷新。
- **新系统已经把这些客户可见效果去掉了**（`grep "【转草单】|【草单更新】" mailbots_next/` = 0，只有企微通知里那个 `🔄 草单更新`）。**这是有意的**——洋 9-17 定过"**客户可见的正文/主题不得有自撰文案**"，并已由 `test_26` 锁住。

⇒ 所以准确表述是：**A/B 现在只影响发给运维的企微通知文案，对客户完全无影响**。

### 2.2 「建空表止损」能止住报错，但会留下一个「永不成立的功能」

建空表后报错会消失，`draft_category` 恒为 A（与现在的**实际行为**一致）。但代码里会永久留着"读一张永不变的表 + 判一个永不成立的条件"，**下次有人看到会以为是活功能**，甚至可能想办法"修好它"（然后踩上 §2.3 的坑）。⇒ 若决定不要这个功能，应当**删掉**，而不是"建表让它别报错"。

### 2.3 🔴 「补写入逻辑」**不该做**（这条我要明确否掉）

小叽的根治方案第 2 条给了两个选项，其中"补写入逻辑（转发成功后 `INSERT code_num`）"**看起来是正道，其实是死路**，原因是根因层面的：

> **人工转发对机器人不可见** —— 机器人不监控任何「已发送」文件夹，它对"客户手上是什么版本"的认知**只包含它自己发过的那些**。

只要发生过一次人工转发，这个台账就不再代表"客户手上有什么"。举个最坏的例子：

```
机器人转过 v1（台账记 v1）
同事人工转发了 v2（台账不知道）
客户回了 v3 —— 机器人拿 v1 的台账去比，v3 不在台账里 ⇒ 判 A（"新草单"）
```

⇒ **补写入之后，"更新"结论依然不可信**——只是从"恒 A"变成"随机准/不准"，那比恒 A 更危险（洋的原则是**宁可漏标，绝不误标**）。

**历史证据也支持这一点**：老系统就是"只看这票转过没、完全不看内容"，实测 **60 封真草单 → B 标 17 封，其中 6 封（35%）是纯重复误标**。洋据此定下的方向是：

> **宁可漏标，绝不误标。**

而 **"恒 A" 恰好就是"绝不误标"** —— 也就是说，**现在的行为在语义上是对的，错的是"它靠一个不存在的表来实现"**。

## 3. 推荐方案（三层）

### A. 代码根治：把 A/B 判定与台账**一起移除** ✅ 推荐

**做什么**（具体到点）：

| 位置 | 改动 |
|---|---|
| `core/extractors/draft.py:35` | B 分支删除，`draft_category` 直接取 `"A"` |
| `core/extractors/draft.py:94-105` | 整个 `_get_draft_nums()` 删除（连同它的 except + `send_program_error`） |
| `serve.py:430-436` | `draft_category == "B"` 分支删除，一律走 `send_forwarded` |
| `core/notify.py:188` | `send_draft_update()` 删除（删掉上面那处后**它就是死代码**；`grep` 确认生产调用点只有 `serve.py:431` 一处） |
| 配置 | `DRAFT_NUMS_DB_PATH`（`settings.py:12`）与 `draft_nums.db` 一并清除（含 `provider.py:119`、`config/__init__.py:80`、conftest 里的环境变量） |
| 测试 | `test_core.py` 里自建 `forwarded_drafts` 的夹具、以及 `send_draft_update` 的三处断言（`test_core.py:976/999/1039`、`test_inbound.py:50`、`test_notify_email.py:113-115`）相应清理 |
| 新锁 | 加一条用例锁住"**草单分类不再触碰任何 DB**"（防有人日后又加回台账读取） |

**为什么推荐删、而不是建空表**：

1. **语义正确**：恒 A = 永不误标 = 洋的既定方向；
2. **消除结构性缺陷**：不再有"读一张没人建的表"这种隐藏地雷；
3. **无状态依赖**：不需要维护台账 ⇒ 没有"人工作业不可见""表损坏/清空后判定退化"这类问题；
4. **告警刷屏的源头自然消失**（这一条也不用靠折叠去掩盖）。

**「重新启用更新/作废」怎么办**：作为**独立的未来工程**登记（`README` 技术债表），并写明**三项前置**，缺一不可：

1. 台账（记录"机器人转发过什么"）；
2. **内容指纹**（箱号 + 文档类型 + 文件名时间戳/md5 —— 用来判断"和上一版是否真的不同"）；
3. **人工转发的可见性**（否则"更新"在语义上不成立 —— 这是根因）。

> ⚠️ 另外要注意：草单命名自带**秒级时间戳**（`<箱号>-<yymmdd>-<hhmmss>已加密.pdf`），**同票重发的文件名必然不同**；而 md5 **单向可靠**（相同 ⇒ 绝对没变；不同 ⇒ 可能只是重新导出）。所以"内容指纹"这块本身也需要单独设计，**不是顺手能做的**。

### B. 通知折叠（你明确要求的那件）

**目标**：把"短时间同类错误刷屏"压成一条，**但不丢信息、不掩盖问题**。

**设计要点**（拟）：

| 维度 | 做法 |
|---|---|
| **在哪做** | `core/notify.py` 的 `WeComNotifier`（通知的单一咽喉；日志与计数都在它这层下面，不受影响） |
| **按什么聚合** | **错误指纹** = `notify_type` + 错误类型/来源 + 消息模板（例：`program_error / draft nums read failed / no such table: forwarded_drafts`）。**不同指纹绝不合并**（否则会把两个不同问题混成一条，反而更难查） |
| **只折叠哪类** | ✅ 只折叠 **`program_error`（程序错误）**；❌ **`alarm` / `pending` 不折叠**——它们每条对应**不同的业务对象**（某箱、某票），折叠会丢信息；`digest` 本身就是汇总，不动 |
| **窗口行为** | 固定窗口（拟默认 **60 秒**）：① **同类首条立即发**（绝不延迟——告警不能等窗口结束才发）② 窗口内同类只累加计数、不发 ③ 窗口结束时若累计 > 1，**补发一条**"（同类错误最近 60 秒共发生 N 次，已折叠）" ④ 错误持续 ⇒ 每个窗口重复 ⇒ 稳态从"每秒 8 条"变成"**每分钟 1 条**" |
| **不折叠的东西** | **日志仍逐条 ERROR**（不变）；**`notify_failed` 计数仍逐次 +1**（不变）⇒ 折叠只减少"发到企微的条数"，**不影响任何可追溯性** |
| **线程安全** | 12 条轮询线程会并发调用 ⇒ 聚合状态加锁（沿用现有 `_counter_lock` 模式） |
| **配置** | `NOTIFY_COLLAPSE_WINDOW_SEC`（默认 60；`0` = 关闭折叠） |
| **进程退出** | 因为"首条已立即发过"，退出时**不会零告警**；只是"共 N 次"这个补充可能丢 ⇒ 可选优化：在正常关闭路径补发一次。**建议先不做**（少一处状态），列为拍板项 |

**⚠️ 关键取舍（要你定）**：折叠会让"一个持续故障"从"每条一发"变成"每分钟一条"。**好处**是不刷屏，**代价**是"故障持续了多久"不再一眼可见（要靠计数/日志）。我建议窗口取 **60 秒**——足够压住刷屏，又不至于让持续故障显得像"只发生过一次"。

### C. 测试盲区（这次事故真正的"帮凶"）

**问题**：`test_core.py` 自己建了 `forwarded_drafts` 表（还有 `test_manifest_spec.py` 自己建 `import_batch`），于是"**代码读一张生产从未建过的表**"这种事，测试全绿也照样上线。

**改法**（两条，都很小）：

1. **本次**：若采纳 §3-A（删功能），测试里那段自建表代码直接删掉；
2. **模式层**：新增/复用**一条"生产初始化冒烟"**用例——**不自己建任何表**，走真实的模块初始化，断言"代码会读的每一张表都存在"。**这类用例能一次性拦住以后所有同类问题**（比逐个排查强）。
   - 我可以顺手做一个小工具：从代码里抽取 `SELECT/INSERT/UPDATE/DELETE` 引用的表名，与 `CREATE TABLE` 清单做差集 ⇒ 有人在 CI 里跑就成了"表引用守卫"。**要不要做，你定。**

## 4. 影响评估

| 方面 | 影响 |
|---|---|
| **给客户发信** | **0 影响**（现在也不受影响；删除后同样不影响） |
| **企微告警** | 删掉读取 ⇒ 刷屏源头消失；叠加折叠 ⇒ 以后任何批量错误也不会刷屏 |
| **运维可见性** | 少一个"草单更新"通知文案（而它**现在本来也发不出来**——恒 A ⇒ 一直是 `Email forwarded`）⇒ **实际可见性零损失** |
| **代码** | 删掉一条"读不存在的表"的路径 + 一个死方法 ⇒ 净减少代码 |
| **风险** | 低：删除的都是"现在实际不生效"的分支（改前后行为一致） |
| **未来** | "更新/作废"若要做，需要按 §3-A 的三项前置单独立项（不是"顺手修好"能到的） |
