## 0. 一句话目标

1. 舱单导入新建的记录**必须能带上「负责公司」**——由毛骁洋在确认页选（下拉，批量默认 + 单行可改）。

## 1. 背景（现状均为实读代码，行号可直接核）

### 1.1 新建行没有负责公司

- `apply_diff` 的新增通道 INSERT 列清单里**没有**「开票子公司名称」：`manifest_engine.py:793-799`。
- `_add_import` 携带的字段只有 客户编码/箱号/封号/箱属/口岸/发班时间：`manifest_engine.py:698-705`。
- 后果：舱单导入新建的行**负责公司为空**。负责公司要等 **Excel 台账导入**才补（`import_excel.py:239-243` 用 `config.ALL_FIELDS` 全列写入）。
- 而「客编 → `records.开票子公司名称`（负责公司）→ 负责同事」是**全系统路由的基础**（`config.py:166-171` `USER_COMPANIES`、`:209-217` `company_to_name`、`:195-206` `sender_for_company`）。负责公司为空 ⇒ 企微通知与邮件路由都找不到人。

### 1.2 退舱重现：只拦，没有出口

- `load_records` 把退舱整条剔出匹配池：`manifest_engine.py:462-468`。
- 于是退舱客编在源清单重现时 `cands` 为空 → 走「陌生客编一律放行」→ 当新记录插入：`manifest_engine.py:528-554`、`:798`。
- 现行行为**已被测试锁定**：`mailbots_next/tests/test_manifest_spec.py:76-83` 断言「退舱客编视同不存在 → 进 imports」。**改本 spec 必须同步改写该用例**（详见 §4 验收 8）。
- 毛骁洋的业务定义（2026-10-06）：**一个客编先退舱，后续其他下属公司又要了这个客编的舱位时，系统上要同时留下「退舱记录」和「新舱位记录」。** 即「两条并存」是**期望结果**，不是脏数据。
- 但他的两个抱怨必须同时解决：
  - ① 现在这条新行**静默产生**，且**不带负责公司**；
  - ② 若把退舱客编放进对比池，**每次导入都要报"重复客编"**，很烦。

> 设计取舍（洋已确认）：**不进池（不产生日常噪音）+ 只在真的重现时问一次 + 记住他的判断（A 为暂缓中间态，可撤销 / 可改判，非永久压制）。**

## 2. 改动一：新建行带「负责公司」（下拉）

### 2.1 前端（`templates/manifest.html`）

在导入确认页的新增清单区域：

1. 表头已显示「负责公司」列（`:421`、`:440`），**新增行该列现在是空的**——改为**可编辑的下拉**。
2. 在新增清单上方给一个**批量默认下拉**：选择后应用于本批**所有尚未单独指定**的新增行。
3. **每行可单独改**（单行覆盖批量默认值）。
   - 理由：一个班列的新客编**可能分属不同下属公司**（专列里混编散舱客编、以及"退舱后换公司重订"都是这种情况），不能整批只能填一个。

### 2.2 后端

1. `_add_import` 的 row 携带 `负责公司`（来自确认页提交值）。
2. `apply_diff` 新增通道的 INSERT 列**加入「开票子公司名称」**：`manifest_engine.py:793-799`。
3. **注意**：`MANIFEST_WRITABLE`（`config.py:129`）是"**更新**通道可覆盖字段"的白名单，**不应**因为本次改动把「开票子公司名称」加进去。本次只允许在**新增**行时写入，**不得**让既有行的负责公司被导入覆盖。

4. 未选择时的兜底：留空（保持现状），**不要**写死一个默认公司——写错公司比留空更难排查。

## 3. 改动二：终态重现的「二选一出口 + 只问一次」

### 3.1 检测（保留既有设计意图）

在 `build_diff` 内，建立终态索引（`by_core_term`，key = `code_core`，仅含 `状态='退舱'` 的记录），并加载暂缓池标记（`manifest_terminal_defer`）。主循环 `if not cands:` 分支必须按下列**判定顺序**处理（顺序错会导致误弹或漏建）：

1. **先查暂缓池标记**（`manifest_terminal_defer` 按 `core`）：
   - `A暂缓` → 跳过（不弹、不建），`continue`；
   - `B改判` → 直接走新增通道（行数据取自当次源行），`continue`。
   - 两种都**不进入**下方终态索引判定。
2. **再查 `by_core_term` 终态索引**：命中 → 产出「终态重现」待确认项，`continue`。
3. **最后陌生客编放行**：既无暂缓标记、又无终态记录 → 原有 `_add_import` 逻辑。

- ⚠️ **判定口径与失效口径不同（务必分清）**：
  - **判定命中**（本条第 1 步查暂缓池）**只按 `core`**——「只问一次」针对**客编**、不区分班列。例：客编 X 在 T1 暂缓，现在导入 T2 含 X（T2 ∈ 本批、T1 ∉ 本批）→ 仍命中 A 暂缓、跳过（行为正确，不弹）。
  - **自动失效**（§3.3.3）**按 `core + train`**——仅当 X 所属班列 ∈ 本批导入班列且源清单不含 X 才失效，避免「只导入部分班列」误杀标记。
  - **同一客编仅一条暂缓/改判记录**（`manifest_terminal_defer UNIQUE(core)`）：撤销=删行，改判=`UPDATE decision`；若该客编在另一班列再次触发，按 `ON CONFLICT(core) DO UPDATE` **覆盖**（同一客编只留一条，业务上合理，后触发覆盖早先记录）。执行方勿按 train 去匹配判定命中，也勿因 UNIQUE 冲突而报错中断。

- **D 的修正（重要）**：终态集合**只含「退舱」**：
  ```python
  TERMINAL_STATUSES = {"退舱"}
  ```
  **不得**把「延期」放进终态——毛骁洋 2026-10-06 明确「延期不是终态」。原 spec 里的 `{"退舱", "延期"}` 作废。
- 因此 `load_records` 的过滤条件**保持不变**（仍只排除退舱 + 软删），不要按原 spec 改成"排除全体终态"。

### 3.2 出口（本次新增，替代原 spec 的"只拦截"）

命中终态重现的行**不再直接 `continue` 丢弃**，而是产出**一条可确认项**，在确认页给三选一：

| 选项 | 语义 | 系统动作 |
|---|---|---|
| **A.「渝新欧还没操作」** | 是同一票，渝新欧侧还没退 | **本次不新增**；该客编记入**暂缓池（中间态）**；默认下次导入不再弹；但暂缓池支持把它「捞出」重新处理（见 §3.3 两操作） |
| **B.「已退舱，新需要」** | 是新的一票 | **放行，正常走新增通道**（当次选 B **不写暂缓池**——新行落库后下次 `cands` 非空、自然不再弹）；该行填/选负责公司（同改动一） |
| **C.「稍后处理」** | 暂不决定 | **不落暂缓、不记忆**；保持现状，下次导入命中该客编**照常再问** A/B/C |

- 默认**不预选**任何一项。必须是人的显式动作，不得默认放行。
- 选 A 时**不得**修改那条退舱记录的任何字段（`AGENTS.md` §6.1 铁律 2）。选 B 时原退舱记录同样**逐字段不动**，仅新增一行新舱位记录。
- A 是**暂缓中间态**而非终局：记入暂缓池后默认「只问一次」，但用户随时可在暂缓池管理页把它**撤销暂缓**（重新激活）或**改判为 B**（详见 §3.3），因此 A 不会永久压制该客编的后续处理。
- ⚠️ **当次选 B 与暂缓池改判 B 区分**：当次选 B 只是建了新行，靠新行自然实现「下次不弹」，**无需落盘**；只有 §3.3.2 两操作②的「暂缓池改判 B」才写 B 标记。表格「下次不再弹」是结果描述，不等于「选 B 也要写暂缓池」——执行方勿误写。

**前端交互约定（确认页）**：每个「终态重现」待确认项在确认页**独立渲染为一行**，含客编 / 箱号 / 原退舱记录 id / 当次源行摘要；提供 **A/B/C 三个互斥选项**（单选按钮或按钮组），**默认不预选**。提交时随 `diff["terminal_decisions"]` 回传（结构见 §3.3.0），与现有 `alerts_applied`（字段冲突确认）通道**并列不混淆**——终态重现走 `terminal_decisions`，字段冲突走 `alerts_applied`。

### 3.3 三层数据流 + 暂缓池存储 + 两操作

#### 3.3.0 选择的三层流转（数据流向，防执行方放错层）

终态重现的选择**绝不能写在 `build_diff` 里**（`build_diff` 是纯 diff 计算，此时用户尚未选）。

- **`build_diff`（只产不出）**：检测到终态重现 → 在 `alerts` 追加一条 `type="终态重现"` 的待确认项，携带 `core`、`record_id`（原退舱记录 id）、`pending_row`（当次源行归一化数据，供 B 落地 & 前端展示）。`pending_row` **必须包含 `is_dedicated`**（专列/散舱判定结果）——由 `build_diff` 在 `if not cands` 分支内已算出的 `_train_is_dedicated(tn)` 填入（见 `manifest_engine.py:519-521,541`），供 B 建行时决定 `imports` 行的「班列类型」。B 建行不重算专列阈值，直接用 `pending_row["is_dedicated"]`。**不写暂缓池、不建行。**
- **前端确认页**：渲染每个「终态重现」项（见 §3.2 交互约定），用户显式选 A/B/C，提交时回传 `diff["terminal_decisions"]`。
- **`apply_diff`（落盘）**：消费 `diff["terminal_decisions"]`（结构见下）按决策写库：
  - **A** → 写暂缓池（`core`, `train`, `decision="A暂缓"`, `decided_at`, `decided_by=operator`）；不建行。
  - **B** → 用 `pending_row`（含 `is_dedicated`）+ 该项 **`company`**（所选负责公司，未选为空串）走新增通道建新行（同 `imports` 路径，`_add_import` 的 `ttype` 用 `pending_row["is_dedicated"]` 决定「专列/散舱」）；**不写暂缓池**（新行落库后下次 `cands` 非空，自然不弹）。负责公司**复用「新增清单」那套选择结果**（`imports` 行的负责公司下拉：批量默认 + 单行覆盖，未选留空），终态重现区**不再另设下拉**——B 行的 `company` 与同批普通 `imports` 行共用同一套取值。`company` 写入新行的 `开票子公司名称`（按改动一）。
  - **C** → 不写库、不建行。

`terminal_decisions` 结构：

```python
diff["terminal_decisions"] = [
    {"core": "C12345", "record_id": 882, "decision": "A", "company": ""},   # A / C 不填 company
    {"core": "C67890", "record_id": 900, "decision": "B", "company": "太平洋"},  # B 必带负责公司（未选为空串）
    # ...
]
```

（`record_id` 用于前端定位原退舱记录；`decision` 取值 `"A"/"B"/"C"`；`company` 仅 B 使用、写入新行 `开票子公司名称`，A/C 留空。build_diff 产出的 `alerts` 项与回传项以 `core`/`record_id` 对应。）

#### 3.3.1 暂缓池存储（硬约束）

- **新增一张轻量表** `manifest_terminal_defer`，**不碰 `yxo.db` 既有表结构**。
- ⚠️ **禁止复用 `apply_diff` 的 `alerts_applied` 分通道机制**（`manifest_engine.py:815-829` 是「已应用的字段覆盖」语义，与「本次暂缓备忘录」语义相反）。暂缓池是独立小表。
- **建表位置**：在 `app.py` 的 `init_db()` 内、紧邻 `update_log` 建表与 `_ensure_update_log_extra_cols(conn)` 调用处（`app.py:330` / `:349`）新增 `CREATE TABLE IF NOT EXISTS manifest_terminal_defer (...)`，随应用启动执行、幂等。
- 表结构（建议）：
  ```sql
  CREATE TABLE IF NOT EXISTS manifest_terminal_defer (
      id         INTEGER PRIMARY KEY,
      core       TEXT NOT NULL,
      train      TEXT,                 -- 班列号：自动失效判定需按班列限定（见 §3.3.3）
      decision   TEXT NOT NULL,       -- 'A暂缓' | 'B改判'
      decided_at TEXT NOT NULL,
      decided_by TEXT,
      UNIQUE(core)                    -- 同一客编仅一条；撤销=删行，改判=UPDATE decision
  );
  ```
- **必须可见**：舱单页或确认页要有入口能翻到「已暂缓 / 已改判的客编」。

#### 3.3.2 两操作（洋 2026-10-09 拍板 · 方案甲）

1. **撤销暂缓（重新激活）**：把该客编从 `manifest_terminal_defer` 删行，回到未决定状态。下次导入命中该客编时（见 §3.1 判定顺序第 1 步），**重新弹 A/B/C**，不直接放行、也不直接建行。
2. **改判为「已退舱，新需要」（B）**：`UPDATE manifest_terminal_defer SET decision='B改判' WHERE core=?`。下次导入命中该客编时（见 §3.1 判定顺序第 1 步），**不再弹终态重现确认**，直接走新增通道进 `imports`；**原退舱记录逐字段不动**；负责公司按改动一在确认页手选（批量默认 + 单行覆盖，未选留空）。

**关于源端行数据（洋确认）**：暂缓池**不需要保存源端行快照**（撤销/改判后下次导入时字段从当次源行来；`B改判` 标记仅决定「下次直接走新增」，建行发生在下次导入命中、走新增通道时，凭当次 `pending_row` 落地）。

#### 3.3.3 「只问一次」语义 + 自动失效

**「只问一次」的准确语义**：
- 仅对「仍处暂缓（`manifest_terminal_defer` 有 `A暂缓` 标记）、未撤销、未改判」的客编生效——默认下次导入不再弹终态确认。
- **撤销暂缓后重新问**；**改判为 B 后不再问**（直接走新增，见 §3.1 第 1 步）。

**自动失效（⚠️ 必须按班列限定，否则会误杀）**：
- 源清单"不含某客编" **≠** 该客编真退了——可能本次只导入了别的班列、没覆盖到它。因此自动失效**必须限定在该客编所属班列 ∈ 本批导入班列（`batch_codes`）且源清单不含该客编时**才触发**（与方案 C 同口径）。
- 实现：build_diff 已有 `batch_codes`（train→set(core)）。对暂缓池中每条记录，取其 `train`：
  - `train ∉ batch_codes` → 本批没覆盖该班列，**不失效、不处理**（保留标记）。
  - `train ∈ batch_codes` 且 `core ∉ batch_codes[train]` → 该班列本批真不含该客编，按下列分情形处理：
    - **A暂缓**：标记**自动失效**（删行），无副作用、不弹不建。
    - **B改判**：**不自动失效**，保留 B 标记，并给出可见提示「该客编此前已判为新增，源端现已不含，请复核」（确认页或舱单页展示）。**不得静默覆盖用户的 B 决定。**
- 若该客编本地状态发生变化（如本地退舱记录被手动改回正常），应清除或重评其标记，不要永久压着。

### 3.4 方案 C（源端缺失 → 建议退舱告警，并入本文）

> 原 `tmp/spec_舱单导入_退舱终态重现拦截.md` 的「方案 C」**已并入本文**（其方案 A / 改动 D 作废）。本文为唯一实现基线，不再依赖那份已取代的文档。

在 `build_diff` 主循环结束后（`return` 之前），新增一段：扫描「本次导入覆盖的班列内、源清单已不含的 active 客编」，产「建议置退舱」告警（**不自动改**）：

```python
    # 方案 C：反向缺口。库内 active 记录，其班列在本批导入范围内、
    # 但客编未出现在本次源清单 → 源端可能已操作退舱，建议人工确认置退舱。
    # 仅限 train ∈ batch_codes 的班列（避免"只导入部分班列"误报其它班列的正常记录）。
    for r in active:
        tn = r["train"]
        if not tn or tn not in source_cores_by_train:
            continue
        if r["core"] in source_cores_by_train[tn]:
            continue  # 源端仍有该客编，正常
        alerts.append({
            "type": "源端缺失建议退舱",
            "key": f"missing:{r['id']}",
            "客户编码": r["code"], "箱号": r["box"],
            "说明": f"库内记录（id={r['id']}，班列 {tn}）状态为「{r['status'] or '正常'}」，"
                    f"但本次导入源清单未含该客编——请确认渝新欧是否已操作退舱，"
                    f"若是则手动置退舱（本系统不自动改）。",
        })
```

**语义要点**：
- 仅在 `train ∈ batch_codes`（本批导入涉及的班列）内判断 → 部分班列导入不会误报其它班列。
- 不写库、不自动置退舱，仅告警交人工处理（洋拍板）。

## 4. 验收标准

1. **负责公司写入**：源清单含 2 个陌生客编 + 确认页分别选「太平洋」「东盟」→ `apply_diff` 后两行的 `开票子公司名称` 分别为对应值。
2. **批量默认 + 单行覆盖**：批量默认选「太平洋」，其中一行单独改「东盟」→ 结果为 1 行太平洋 + 1 行东盟。
3. **不选则留空**：未选择时写入空字符串，**不写默认公司**。
4. **既有行不被覆盖**：库内一条已有记录（负责公司=「保时达」）走更新通道 → 其 `开票子公司名称` **不得**被本次导入改写。
5. **终态重现·选 B**：库内 1 条 `状态=退舱`（core=X）+ 源含同 core 的 active 行 + 选择「已退舱，新需要」→ 新增 1 条 `状态=正常` 的记录、负责公司按所选写入；**原退舱记录逐字段未动**。
6. **终态重现·选 A**：同上条件 + 选择「渝新欧还没操作」→ `imports` 中**不含** X、库内**无新增行**、原退舱记录逐字段未动。
7. **只问一次（暂缓态）**：在验收 6（选 A 进暂缓池）之后，**再跑一次同样的 `build_diff`**（源仍含 X）→ 该客编**不再**产生终态重现待确认项，库内仍无新增；命中暂缓池标记直接跳过终态确认。
8. **⚠️ 必须同步改写既有测试**：`mailbots_next/tests/test_manifest_spec.py:76-83` 现断言「退舱客编 → 进 imports」，**正是本次要改的行为**，必须改写为按 §3.2 的 **A / B 两支分别断言**（A→不进 imports + 进暂缓池；B→进 imports + 新行带负责公司 + 班列类型按 `is_dedicated` 写对专列/散舱）。另须**增补**撤销暂缓（验收 11）、改判为 B（验收 12）、A/B 自动失效（验收 13、14）的对应用例。
   - 同文件另一条阈值测试（`:86`，41 客编含 5 退舱 → 有效 36+1=37 ≤40 判散舱、退舱不膨胀阈值）**保持不变**。
9. **延期不参与终态**：库内 1 条 `状态=延期`（core=Z）+ 源含 Z → **不得**产生终态重现待确认项，走正常匹配/更新路径。
10. **回归**：`mailbots_next/tests/` 全套通过；`TERMINAL_STATUSES` 在仓库内只有一个定义处。

11. **暂缓池·撤销暂缓**：验收 6 后，将该客编从暂缓池**撤销暂缓（重新激活）** → 再跑 `build_diff`（源仍含 X）→ **重新产生**终态重现待确认项（A/B/C），不直接放行、不直接建行。
12. **暂缓池·改判为 B**：验收 6 后，将该客编**改判为「已退舱，新需要」** → 再跑 `build_diff`（源仍含 X）→ **不再弹**终态确认，X **进 `imports`**，新行 `状态=正常`、负责公司按所选写入、原退舱记录逐字段未动；未选则负责公司留空。
13. **暂缓池·A 自动失效（班列限定）**：验收 6 后，构造**同班列、源清单不再含** X 的 `build_diff` → A 暂缓标记**自动失效**（删行），不弹不建；若构造**不同班列**的导入（未覆盖 X 所属班列），X 标记**保留不失效**（不误杀）。
14. **暂缓池·B 改判不自动失效**：验收 6（改判 B）后，源端（该班列内）消失 → B 标记**不自动失效**，保留标记 + 可见提示「该客编此前已判为新增，源端现已不含，请复核」；不得静默覆盖 B 决定。
15. **存储隔离**：暂缓池为**新增独立轻量表** `manifest_terminal_defer`，`yxo.db` 既有表（`records` / `update_log` 等）**结构未被改动**；未复用 `alerts_applied` 机制；表在 `app.py init_db` 内 `CREATE TABLE IF NOT EXISTS` 随启动建好。

## 7. 未钉死点的正式裁定（洋 2026-10-10 终审 · 验收通过）

> OpenCode 实现时遇到 spec 未钉死的 3 处点，按下列裁定实现；芙蕾雅逐行核验代码（含 `manifest_engine.py` 行号）确认与 spec 一致，验收通过。本节奏定为**正式结论**，保持 spec 与代码一致。

### 7.1 B 行「负责公司」取值 = 批量默认当前值
- 当次选 B 走新增通道建行时，其 `company` 取自确认页回传的 `terminal_decisions[].company`；该值**复用「新增清单」那套选择结果**（批量默认 + 单行覆盖，未选为空串），终态重现区**不另设下拉**（见 §3.3.0 第 3 点）。
- 依据：spec §2.2（单行覆盖优先、终态区不另设下拉）+ §3.3.0（B 行 `company` 与同批普通 `imports` 行共用同一套取值）。
- 代码落点：`apply_diff` `company = t.get("company")`（`manifest_engine.py:1006`），写入新行 `开票子公司名称`（:1016）；`pending_row` 不含公司字段，公司由前端随决策回传。

### 7.2 自动失效删行时机 = build 只算、apply 删行，且按 `core + train` 限定
- `build_diff` **只计算** `defer_expired` 清单（含 A 到期 + 失的标记），**绝不写暂缓池、绝不删行**（注释 `manifest_engine.py:782`「build 不写暂缓池」）。
- 真正删行在 `apply_diff`（`:974-978`）。
- 失效口径（与判定口径不同，见 §3.1）：A 暂缓仅在 `train ∈ batch_codes 且 core 全局缺席`时到期删行（`:804-808`），防「只导了别的班列」误杀；B 改判**永不自动失效**，仅给「改判复核提示」可见告警（`:794-803`），不静默覆盖用户决定；本地退舱记录消失（`core not in by_core_term`）→ 失的标记清 `defer_expired`（`:790-793`）。
- 依据：spec §3.3.3（必须按班列限定）+「build 不写暂缓池」铁律。

### 7.3 B 改判永不自动失效
- 见 7.2 与 spec §3.3.3：B 标记（无论当次选 B 不落池、还是暂缓池改判 B）均**不自动失效**，仅源端消失时给复核提示。

### 7.4 方案 C 按原文不收窄
- `build_diff` 方案 C（`:811-828`）严格按 spec §3.4 原文实现：仅限 `train ∈ batch_codes` 的班列内、源清单已不含的 active 客编产「源端缺失建议退舱」告警，**不自动改**、不收窄范围。
- 洋 2026-10-10 裁定：**方案 C 噪音范围维持 spec 原文**（如需进一步收窄为独立优化项，另行立项，不在本 PR 范围）。
