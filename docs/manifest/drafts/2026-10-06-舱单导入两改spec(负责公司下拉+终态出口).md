# Spec：舱单导入两改 —— 负责公司下拉 + 终态重现出口

> **给谁**：执行本 spec 的智能体（OpenCode）。**读者只有执行方**，不写讨论过程。
> **作者**：雪儿｜**日期**：2026-10-06｜**状态**：待毛骁洋拍板
> **基线**：`main`，**从 `main` 切扁平命名的临时分支**（如 `fix-manifest-company-and-terminal-exit`）
> **范围**：`manifest_engine.py` 的 `build_diff` / `apply_diff` + `templates/manifest.html` 的确认页 + 配套测试
> **与既有文档的关系**：本文**取代并改写** `tmp/spec_舱单导入_退舱终态重现拦截.md` 的「方案 A」与「改动 D」；该文档的「方案 C（源端缺失建议退舱）」**仍然有效，按原文实现**。

---

## 0. 一句话目标

1. 舱单导入新建的记录**必须能带上「负责公司」**——由毛骁洋在确认页选（下拉，批量默认 + 单行可改）。
2. 退舱客编重现时，**不是干拦截，而是给一个二选一的出口，并且只问一次**。

---

## 1. 背景（现状均为实读代码，行号可直接核）

### 1.1 新建行没有负责公司

- `apply_diff` 的新增通道 INSERT 列清单里**没有**「开票子公司名称」：`manifest_engine.py:793-799`。
- `_add_import` 携带的字段只有 客户编码/箱号/封号/箱属/口岸/发班时间：`manifest_engine.py:698-705`。
- 后果：舱单导入新建的行**负责公司为空**。负责公司要等 **Excel 台账导入**才补（`import_excel.py:239-243` 用 `config.ALL_FIELDS` 全列写入）。
- 而「客编 → `records.开票子公司名称`（负责公司）→ 负责同事」是**全系统路由的基础**（`config.py:166-171` `USER_COMPANIES`、`:209-217` `company_to_name`、`:195-206` `sender_for_company`）。负责公司为空 ⇒ 企微通知与邮件路由都找不到人。

### 1.2 退舱重现：只拦，没有出口

- `load_records` 把退舱整条剔出匹配池：`manifest_engine.py:462-468`。
- 于是退舱客编在源清单重现时 `cands` 为空 → 走「陌生客编一律放行」→ 当新记录插入：`manifest_engine.py:528-554`、`:798`。
- 现行行为**已被测试锁定**：`mailbots_next/tests/test_manifest_spec.py:76-83` 断言「退舱客编视同不存在 → 进 imports」。**改本 spec 必须同步改写该用例**（详见 §4 验收 8）。
- 毛骁洋的业务定义（2026-10-06）：**一个客编先退舱，后续其他下属公司又要了这个客编的舱位时，系统上要同时留下「退舱记录」和「新舱位记录」。** 即「两条并存」是**期望结果**，不是脏数据。
- 但他的两个抱怨必须同时解决：
  - ① 现在这条新行**静默产生**，且**不带负责公司**；
  - ② 若把退舱客编放进对比池，**每次导入都要报"重复客编"**，很烦。

> 设计取舍（洋已确认）：**不进池（不产生日常噪音）+ 只在真的重现时问一次 + 记住他的判断。**

## 2. 改动一：新建行带「负责公司」（下拉）

### 2.1 前端（`templates/manifest.html`）

在导入确认页的新增清单区域：

1. 表头已显示「负责公司」列（`:421`、`:440`），**新增行该列现在是空的**——改为**可编辑的下拉**。
2. 在新增清单上方给一个**批量默认下拉**：选择后应用于本批**所有尚未单独指定**的新增行。
3. **每行可单独改**（单行覆盖批量默认值）。
   - 理由：一个班列的新客编**可能分属不同下属公司**（专列里混编散舱客编、以及"退舱后换公司重订"都是这种情况），不能整批只能填一个。
4. 下拉选项**复用现有数据源**：`config.py:71-72` 的「开票子公司名称」options（8 家公司），该字段 `maintainable: True`，取值存于 `field_options` 表，界面已有维护入口。**不要另建一份公司清单。**

### 2.2 后端

1. `_add_import` 的 row 携带 `负责公司`（来自确认页提交值）。
2. `apply_diff` 新增通道的 INSERT 列**加入「开票子公司名称」**：`manifest_engine.py:793-799`。
3. **注意**：`MANIFEST_WRITABLE`（`config.py:129`）是"**更新**通道可覆盖字段"的白名单，**不应**因为本次改动把「开票子公司名称」加进去。本次只允许在**新增**行时写入，**不得**让既有行的负责公司被导入覆盖。
   - 即：新增通道可写；更新通道**不可**写「开票子公司名称」。请在代码注释里写清这条边界。
4. 未选择时的兜底：留空（保持现状），**不要**写死一个默认公司——写错公司比留空更难排查。

## 3. 改动二：终态重现的「二选一出口 + 只问一次」

### 3.1 检测（保留既有设计意图）

在 `build_diff` 内，按 `tmp/spec_舱单导入_退舱终态重现拦截.md` 的**方案 A.1** 建立终态索引（`by_core_term`，key = `code_core`），并在「陌生客编放行」之前先查它。

- **D 的修正（重要）**：终态集合**只含「退舱」**：
  ```python
  TERMINAL_STATUSES = {"退舱"}
  ```
  **不得**把「延期」放进终态——毛骁洋 2026-10-06 明确「延期不是终态」。原 spec 里的 `{"退舱", "延期"}` 作废。
- 因此 `load_records` 的过滤条件**保持不变**（仍只排除退舱 + 软删），不要按原 spec 改成"排除全体终态"。

### 3.2 出口（本次新增，替代原 spec 的"只拦截"）

命中终态重现的行**不再直接 `continue` 丢弃**，而是产出**一条可确认项**，在确认页给三选一：

| 选项 | 语义 | 系统动作 |
|---|---|---|
| **A.「渝新欧还没操作」** | 是同一票，渝新欧侧还没退 | **本次不新增**；记下「该客编已确认暂缓」；**下次导入不再弹** |
| **B.「已退舱，新需要」** | 是新的一票 | **放行，正常走新增通道**，并在该行填/选负责公司（同改动一） |
| **C.「稍后处理」**（可选） | 暂不决定 | 保持现状，下次再问 |

- 默认**不预选**任何一项。必须是人的显式动作，不得默认放行。
- 选 A 时**不得**修改那条退舱记录的任何字段（`AGENTS.md` §6.1 铁律 2）。

### 3.3 「只问一次」的落盘

需要一个很轻的**暂缓清单**（避免同一客编每次导入都弹）：

- 存储：优先**复用现有确认通道**（`apply_diff` 的 `alerts_applied` 分通道机制，见 `manifest_engine.py:815-829`）。若不方便，则新增一张小表，**不要动 `yxo.db` 既有表结构**。
- 记录字段至少：`客户编码(core)`、`决定`、`决定时间`、`决定人`。
- **必须可见**：确认页或舱单页要有地方能翻到"已暂缓的客编"。
- **必须可撤销**：其他下属公司后来又真的要了这个客编时，能把它改判为「已退舱，新需要」。
- **必须会自动失效**：一旦该客编在源清单中消失（渝新欧真的退了），这条暂缓自然不再被触发；同时若该客编本地状态发生变化，应清除暂缓记录，不要永久压着。

### 3.4 与「方案 C」的关系

`tmp/spec_舱单导入_退舱终态重现拦截.md` 的**方案 C（源端缺失 → 建议置退舱告警）保留，按原文实现**，本 spec 不改它。

## 4. 验收标准

1. **负责公司写入**：源清单含 2 个陌生客编 + 确认页分别选「太平洋」「东盟」→ `apply_diff` 后两行的 `开票子公司名称` 分别为对应值。
2. **批量默认 + 单行覆盖**：批量默认选「太平洋」，其中一行单独改「东盟」→ 结果为 1 行太平洋 + 1 行东盟。
3. **不选则留空**：未选择时写入空字符串，**不写默认公司**。
4. **既有行不被覆盖**：库内一条已有记录（负责公司=「保时达」）走更新通道 → 其 `开票子公司名称` **不得**被本次导入改写。
5. **终态重现·选 B**：库内 1 条 `状态=退舱`（core=X）+ 源含同 core 的 active 行 + 选择「已退舱，新需要」→ 新增 1 条 `状态=正常` 的记录、负责公司按所选写入；**原退舱记录逐字段未动**。
6. **终态重现·选 A**：同上条件 + 选择「渝新欧还没操作」→ `imports` 中**不含** X、库内**无新增行**、原退舱记录逐字段未动。
7. **只问一次**：在验收 6 之后，**再跑一次同样的 `build_diff`** → 该客编**不再**产生终态重现待确认项；库内仍无新增。
8. **⚠️ 必须同步改写既有测试**：`mailbots_next/tests/test_manifest_spec.py:76-83` 现断言「退舱客编 → 进 imports」，**正是本次要改的行为**，必须改写为按 §3.2 的 A/B 两支分别断言。
   - 同文件另一条验收 11（`:86`，41 客编含 5 退舱 → 有效 36+1=37 ≤40 判散舱、退舱不膨胀阈值）**保持不变**。
9. **延期不参与终态**：库内 1 条 `状态=延期`（core=Z）+ 源含 Z → **不得**产生终态重现待确认项，走正常匹配/更新路径。
10. **回归**：`mailbots_next/tests/` 全套通过；`TERMINAL_STATUSES` 在仓库内只有一个定义处。
