## 1. 改动一：陌生客编判定放宽（专列放行）

### 1.1 现状 / 根因
`build_diff` 原本对"库内查不到这个客编"的 Excel 行，只要"它的**班列号**在库里已经存在**任何**箱"，就报 `陌生客编`（疑似写错）并 `continue` 跳过、不导入。

问题：班列可以 **散舱 + 专列混编**。例如 WB883 库里已有 2 个 DMZ 散舱箱，Excel 里又有 52 个 XLYJN 专列客编——原逻辑一看"WB883 已有人"就把 52 个专列客编全当异常丢进报警清单，一个都导不进。

**根因（业务规则 2026-09-14 定）：** 专列的判定依据是"**一个班列号的客编（code_core 去重）总数 > 40**"，而不是"班列是否已存在专列箱"。且专列上合法地可同时有专列客编与散舱客编（专列客户箱数不满列，余箱当散舱由集团拿）。因此原"是否已有专列箱"的判据从根本上错——既会误拒专列补箱，也无法处理整趟新散舱被写死"专列"的问题。

### 1.2 目标行为（专列判定：客编总数 > 40）

对"库内查不到该客编"的 Excel 行，**不再按"班列是否已有专列箱"判拒，一律放行进导入清单**，写入类型按"该班列客编总数"判定：

- **客编总数 = 库内该班列已有客编（code_core 去重） + 本次导入该班列客编（code_core 去重）**，合并去重后统计。
  - **"本次导入"的范围（写死，避免歧义）**：指**所有能解析出班列号、且未被"缺班列号"丢弃（改动一 §1.5）的 Excel 行**，按 `code_core` 去重。包含：最终进 `imports` 的新行、进 `updates` 的已有行、以及处于"字段冲突/弱提示"待确认状态的行。**不包含**：缺班列号被丢弃的行、纯空行/客编缺失行（F7/R0）。退舱是库内状态，Excel 行本身无退舱概念，故不参与"本次"计数（库内退舱已按改动三剔除，不会进 `by_train`）。
- **客编总数 > 40** → 该班列判为**专列**，陌生客编放行写 `专列`（即便库内已有该班列的散舱客编，后续客编仍按专列写）。
- **客编总数 ≤ 40** → 该班列判为**散舱**，陌生客编放行写 `散舱`，并给**黄色弱提示**"该班列客编未达阈值（≤40），按散舱导入，请核对"（不阻断）。
- **库内既有散舱客编**（如专列班列里历史留下的那 7 箱）**原样保留，不改动**。
- 阈值常量 `DEDICATED_THRESHOLD = 40`，统计严格用 `> 40`；客编计数按 `code_core`（去后缀的客户编码）去重，一个客户多箱/多后缀算 1 个客编。

### 1.3 对比（before / after）

| 场景 | 原逻辑 | 改后逻辑 |
|---|---|---|
| 客编库内无，该班列**客编总数(库内+本次) > 40** | 若班列已有箱→报异常拒 | ✅ 放行，写 `专列` |
| 客编库内无，该班列**客编总数 ≤ 40** | 同上→报异常拒 | ✅ 放行，写 `散舱` + 黄色提示核对 |
| 客编库内无，库内**无该班列**（整趟新） | 写死 `专列` ❌ | ✅ 按本次客编数判：>40 专列 / ≤40 散舱 |

### 1.4 实现要点
- **取消**原 `any(r.get("ttype") == "专列")` 的判据：专列判定不再看"是否已有专列箱"，改为统计客编数。
- `build_diff` 开头（或 `load_records` 后）按班列号统计该班列**客编总数**：
  - 库内部分：从 `by_train[train]` 的各记录取 `code_core` 去重计数（已按改动三剔除退舱/软删）；
  - 本次部分：从**本次导入待处理行**（范围见 §1.2，"能解析出班列号且未被缺班列号丢弃的 Excel 行"）取同班列 `code_core` 去重计数；
  - 合并去重得 `train_total_codes`；`is_dedicated = train_total_codes > DEDICATED_THRESHOLD`（=40）。
- `if not cands:`（陌生客编）分支内：不再 `continue` 拒，而是直接 `_add_import(...)`，并把算出的 `is_dedicated` 作为该行的导入类型（专列/散舱）随 diff 携带，`apply_diff` 原样写入（**废除字面写死"专列"**）。
- `by_train` 已在 `build_diff` 开头构建（train → records 列表），直接复用；本次导入行的客编可在遍历首轮先收集。
- **弱提示**：当 `not is_dedicated` 时，对该陌生客编行生成一个**非阻断黄色 alert**（类型 `"弱提示"`，结构见 §8，键 `key = 班列号 + ":" + code_core`），提示语含"客编 ≤40 按散舱导入，请核对"，前端渲染为黄色、不阻断提交；其勾选"已知悉"后的消失交互见**改动四 §4**（不写库、仅从列表移除，映射 `confirmedWeak[key]`）。
- 保留 `load_records` 返回 `客户编码`（供 code_core 派生与计数，通常已有）；改动二所需的 `开票子公司名称`/`箱属` 等字段照 2.3 处理。

### 1.5 配套修正：无班列号新行不再静默丢弃（R3b-1）

**现状：** `_add_import` 内对"班列号为空"的新行直接 `if not tn: return`，该行**凭空消失**——不报警、不写库、用户无感知，属数据丢失风险。

**改后：** 无班列号的新行不再 `return` 丢弃，而是生成一个**可见 alert**（如类型 `缺班列号`、提示"缺班列号，未导入"），进报警清单展示；不写库但不消失，操作员能在页面看到"有 N 行因缺班列号未导入"。

**实现要点：** 将 `_add_import` 的 `if not tn: return` 改为"生成 alert 并汇总"，其余导入逻辑不变。

## 2. 改动二：箱属进更新 / 箱号封号冲突可确认

### 2.1 现状 / 根因
`build_diff` 把 **箱号 / 封号 / 箱属** 三字段捆在同一个"冲突→字段冲突报警"逻辑里：库内非空、文件值又不同 → 报 `字段冲突` 进报警清单、不写库。结果：
- 箱属（COC/SOC）一变就被当异常卡住，无法按"待确认更新"处理；
- 「更新」清单只显示 `客户编码 / 箱号 / 变更明细`，**缺班列号、缺负责公司**，不便截图分发给对应公司；
- 箱号/封号冲突在页面上**只能看、没法确认处理**（前端只对部分类型渲染勾选框）。

### 2.2 目标行为（三小块）
1. **箱属**：库内已有、文件变了 → **进「更新」清单**（待确认更新），不再报警；比较前用 `norm_owner()` 归一化，避免 `coc`/`COC` 大小写误判。库内空、文件有值（补录）也同样进更新。
2. **箱号 / 封号**：冲突保持**报警**，但新增「确认应用」勾选框——勾选即用**文件值覆盖库内**（UPDATE + `update_log` 留痕可回退）；**箱号**确认应用时额外弹**二次确认弹窗**，封号直接应用。
3. **更新清单展示**：每行加「班列号」「负责公司（= `开票子公司名称`）」两列，内容与库一致。

### 2.3 实现要点（按落点）

**`manifest_engine.py` — `load_records`**
- SELECT 需包含 `开票子公司名称`（已在工作区补上），out dict 记为 `company`，渲染时显示名"负责公司"。

**`manifest_engine.py` — `build_diff`**
- **箱属分支**（独立出来，不进冲突报警）：
  ```
  iv_owner = row.get("箱属")
  if iv_owner is not None and iv_owner != "":
      dv_owner = norm_owner(db["owner"])
      iv_owner_norm = norm_owner(iv_owner)
      if dv_owner == "":
          changes.append({"field":"箱属","old":"","new":iv_owner,"action":"补"})
      elif iv_owner_norm == dv_owner:
          pass
      else:
          changes.append({"field":"箱属","old":db["owner"],"new":iv_owner,"action":"改"})
  ```
- **箱号 / 封号 冲突**：保持报 alert，但**两条路径都必须用类型 `"字段冲突"`**（见 2.4 坑）：
  - 单候选、箱号不一致路径（现报 `"箱号冲突"`）→ **改为 `"字段冲突"`**，并**显式在 alert 中携带 `field: "箱号"`**（不要靠说明文本识别，见 §8 数据结构）。
  - 变化循环里的封号/箱号冲突（现报 `"字段冲突"`）→ 维持 `"字段冲突"`，并**显式携带 `field: "封号"` 或 `"箱号"`**。
  - alert 顶层**显式携带 `field` 与 `new_value`**（结构见 §8.1）：`field` ∈ `"箱号"|"封号"`；`new_value` 取值规则见 §8.1（**关键点**：`new_value` 统一从 `row` 顶层取——`field=="箱号"` 取 `row["箱号"]`、`field=="封号"` 取 `row["封号"]`，**对称，opencode 无需记"箱号走 row、封号走 文件值"的不对称规则**；⚠ **不可**从 `文件值` 取 `箱号`——生产 `_alert` 的 `文件值` 字典仅含 (班列号,口岸,发班时间,箱属,封号)，**不含箱号键**，取 `文件值["箱号"]` 得 `None`，会把库内箱号清空）；前端据 `a.field` 决定覆盖逻辑、据 `a.new_value` 写入确认，**不解析说明文本、不靠比对库内值推断**。
- **更新项** `updates.append(...)` 中带上 `班列号: db["train"]`、`负责公司: db["company"]`。

**`manifest_engine.py` — `apply_diff`**
- `alerts_applied` 已支持分通道结构（**新增 `source` 字段区分**，见 §8.2）：`field_fix` 条目 `{source, record_id, field, new_value}` 走 `UPDATE ... SET "<field>"=?`；`suffix_change` 条目 `{source, record_id, new_code, 目的站}` 走 `客户编码`/`目的站` 两列写入（一条覆盖两列）。均 + `update_log` 留痕，old/new 写清。
  - **白名单校验（分通道、服务端强制）**：`apply_diff` 在拼 SQL 前**必须于后端**对 `field` 再校验，即便 `field` 来自前端提交的 `confirmedFieldFix`/`confirmedSuffix` 负载也不得直接信任：
    - `source == "field_fix"`（字段冲突覆盖）→ `field` 必须 ∈ `("箱号","封号")`；
    - `source == "suffix_change"`（后缀变更）→ 仅允许写入列 `客户编码`（来自 `new_code`）与 `目的站`（来自 `目的站`），列名白名单校验；
    - 任一不满足 → **拒绝执行并报警**，绝不允许 `field` 直接拼进 SQL（防误更新 / SQL 注入）。
  - **请确保箱号也走通**（上次另一实现箱号根本没进 confirm 列表，见 2.4）。

**`templates/manifest.html`**
- `renderUpdates`：表头加 `班列号`、`负责公司` 两列，行内取 `u["班列号"]` / `u["负责公司"]`。
- `renderAlerts`：对 `a.type === "字段冲突"` 渲染「确认应用（用文件值覆盖）」勾选框，勾选写入 `confirmedFieldFix[record_id + ":" + a.field] = {field: a.field, new_value: a.new_value}`（**必须用 `record_id + ":" + field` 作键，否则同一记录同时有箱号+封号冲突时会互相覆盖**，见 §8）。
- `_doApply("alerts")`：合并后缀变更 + 字段冲突应用；对 `field === "箱号"` 的条目弹**二次确认**；按钮文案「确认报警」（已有）。
- `updateApplySum`：统计字段冲突数量（已有）。

### 2.4 ⚠️ 上次实现的坑（务必避开）
- **箱号冲突必须能确认**：前端 `renderAlerts` 只对 `type === "字段冲突"` 渲染确认勾选框。若 `build_diff` 在**单候选箱号不一致路径**报的是 `"箱号冲突"`（旧代码就是），前端不渲染勾选框 → **用户无法确认覆盖箱号**。修复：该路径类型改成 `"字段冲突"` 并显式带 `field:"箱号"`（与封号统一，见 §8）。
- 变化循环中箱号/封号的 `字段冲突` 因**单候选路径的 `continue` 提前跳过**而**不可达**，属冗余死代码，实现时可清理（确认逻辑以能达的路径为准）。
- `norm_owner()` 比较必须用在"库内值"和"文件值"**两侧**，否则仍会大小写误判。

## 3. 改动三：退舱记录不参与舱单导入比对

### 3.1 现状 / 根因
`load_records` 当前 SQL 为 `SELECT ... FROM records`，**不过滤 `状态='退舱'`**（也不在 SQL 层过滤 `is_deleted`）。`build_diff` 仅用 `active = [r for r in recs if not r["deleted"]]` 滤掉软删，**退舱记录仍原样进入 `by_core` / `by_train`**，参与全部比对：
- 某客户此前退舱的客编仍在库 → 新导入同客编会命中 `by_core`，被当成"库内已有"而非新行（可能错过补录/更新）；
- 退舱客编计入 `by_train` 的客编总数 → 虚增专列判定阈值（改动一的"客编总数 > 40"会被退舱箱抬高），可能导致本应散舱的班列误判为专列。

这与全项目其它模块的"有效记录铁律" `WHERE 状态<>'退舱' AND COALESCE(is_deleted,0)=0`（邮件机器人匹配、Dashboard 统计、托书箱量均如此）不一致——舱单导入是唯一的例外缺口。

### 3.2 目标行为
舱单导入的所有比对环节（命中库内、箱号消歧、陌生客编判定、客编总数计数）**一律以"有效记录"为基准，退舱记录视同不存在**。

### 3.3 实现要点
- `load_records` 的 SELECT 增加 `状态` 列；SQL 加 `WHERE COALESCE(状态,'')<>'退舱' AND COALESCE(is_deleted,0)=0`（用 `COALESCE(状态,'')` 兼容 `状态` 为 NULL 的行，避免 `状态<>'退舱'` 把 NULL 行错误排除；与项目铁律精神一致），out dict 增加 `"status": (r["状态"] or "").strip()`。
- 如此 `by_core` / `by_train` 天然不含退舱与软删；`build_diff` 内 `active = [r for r in recs if not r["deleted"]]` 可保留（冗余但无害），亦可同步简化为对全量 `recs` 直接用。
- **连带效果**：改动一的"客编总数(库内+本次)"计数自动以有效记录为准，退舱客编不再虚增阈值。
- 注意：`load_records` 目前仅被 `build_diff` 调用，收窄不会影响其它逻辑。
- 退舱记录本身不被本功能改动（不改状态、不写日志），仅"不参与比对"。

## 4. 改动四：已确认 / 已处理的报警从列表消失

### 4.1 现状 / 根因
报警/待处理页（`renderAlerts` 渲染 `LAST_DIFF.diff.alerts`）里，目前只有 `后缀变更` 类带勾选框，且其确认逻辑（`_doApply("alerts")`）在应用成功后**只清空 `confirmedSuffix` 映射、`d.updates`/`d.imports` 数组，从未从 `LAST_DIFF.diff.alerts` 中删除被确认的报警条目**。`renderDiff` → `renderAlerts(LAST_DIFF.diff.alerts)` 每次重渲染都使用原始全量数组，因此已确认的后缀变更（以及后续要支持的字段冲突、弱提示）**确认后仍留在列表、不消失**。

此外当前 `_doApply("alerts")` 仅处理 `confirmedSuffix`，**字段冲突的确认（`confirmedFieldFix`）尚未接入应用与移除**——改动二 2.3 的勾选框确认后会"确认了但不生效、也不消失"。

### 4.2 目标行为
- 报警面板中，**所有可处理的黄色预警**都带勾选框：
  - `后缀变更` / `字段冲突` → 勾选"确认应用"（写库 + 留痕）；
  - `弱提示`（改动一的 ≤40 散舱核对提示，非阻断）→ 勾选"已知悉"（仅确认、不写库）。
- 操作员勾选**部分**条目 → 点「确认报警」→ 已勾选项被应用/确认 → **从 `LAST_DIFF.diff.alerts` 中移除对应条目，并清空其 confirmed 映射**，重渲染后这些条目从列表消失；未勾选的继续保留。

### 4.3 实现要点
- `renderAlerts` 对 `a.type ∈ {后缀变更, 字段冲突, 弱提示}` 均渲染勾选框：后缀变更/字段冲突分别写 `confirmedSuffix`/`confirmedFieldFix`（键见 §8.2），弱提示写入一个"已确认弱提示"集合，**键统一为 `key = 班列号 + ":" + code_core`**（唯一键规则见 §8.1/§8.3，删除"alert 序号"等模糊说法）。
- `_doApply("alerts")` 重写：收集所有勾选项——
  - 后缀变更 + 字段冲突 → 合并进 `alerts_applied`，每条带 `source`（字段冲突=`"field_fix"`、后缀变更=`"suffix_change"`），字段冲突走 `confirmedFieldFix[record_id + ":" + field]`（见 §8 与改动二 2.3）；调用 apply（见失败处理，优先数据库事务）；
    - **suffix_change 条目数据来源（必须写死）**：`_doApply` 组装 `suffix_change` 条目时，`new_code` / `目的站` **从 `LAST_DIFF.diff.alerts` 中该 `record_id` 对应的「后缀变更」原始 alert 读取**——`new_code = alert["客户编码"]`（文件新客编）、`目的站 = alert.get("目的站建议","")`（见 §8.1 该 alert 的键）；`confirmedSuffix[record_id]` **只承担"是否勾选"标记**，不存数据。后缀变更**一条 alert 同时覆盖 `客户编码`+`目的站` 两列**（如其一为空则只写有的列），对应 apply_diff 既有 `new_code`/`目的站` 通道。`old` 值由 apply_diff 端从库内 `fetch` 取得（见生产 `apply_diff` 行 751/762），不依赖 alert 携带。
  - 弱提示 → 不写库，仅标记 `confirmedWeak[key] = true`。
    - **弱提示的"成功"语义（必须写死）**：弱提示**不写库**，其"成功"= 本地已写入 `confirmedWeak[key]`（无需服务端事务参与）；其从列表**移除**的时机 = 同批次的字段冲突/后缀变更事务 `COMMIT` 成功后（或本批无写库项时立即）才执行（见下方"应用/确认成功后"）。即弱提示的移除依附于本批写库事务的结果，自身不产生事务。
  - 应用/确认成功后：从 `LAST_DIFF.diff.alerts` 中**按 `record_id`（弱提示按唯一键 `key`）删除这些已处理条目**；清空 `confirmedSuffix` / `confirmedFieldFix` / `confirmedWeak` 映射；调用 `renderDiff(LAST_DIFF)` 重渲染。
- **失败处理（必须明确）**：`_doApply("alerts")` 应用**优先用数据库事务**——`BEGIN` 包住本批次全部 `UPDATE records` + `update_log`，任一失败 `ROLLBACK`、全部成功 `COMMIT`（若项目已有整库快照/回滚机制则沿用，不必重复实现）。**任一步失败**时：
  - 已处理条目**不移除**（仍留在 `LAST_DIFF.diff.alerts`，便于重试）；
  - **清空** `confirmedSuffix` / `confirmedFieldFix` / `confirmedWeak` **全部确认映射**（重置勾选态），避免部分写库后残留勾选导致重复应用或误判；
  - 事务已回滚，库回到操作前状态，保证"全有或全无"；
  - 向用户提示失败原因，由用户修正后重新勾选确认。
  - 仅当**全部成功（事务 COMMIT）**才执行上一条"移除已处理项 + 清空对应映射"。
- 与改动二的 `字段冲突` 确认打通：改动二 2.3 的 `renderAlerts`/`_doApply` 描述以本改动四为准（确认后须移除 + 纳入 `alerts_applied`）。

## 8. 附录：数据结构约定（alert 与确认映射统一结构，改动一/二/四 共用）

为避免前端 `manifest.html` 与引擎 `build_diff` / `apply_diff` 之间结构不一致导致"同记录多字段互相覆盖 / 无法识别"等问题，下列结构为**强制约定**，改动一 / 改动二 / 改动四 必须严格遵循。

### 8.1 alert 统一结构
引擎 `build_diff` 产出的每条 alert 必须是下列形态之一（JS 对象示意）：

```js
// 字段冲突（改动二）：build_diff 产出的【原始展示 alert】——前端据 a.field / a.new_value 渲染勾选框
// 注意：字段冲突 alert 必须显式携带 field 与 new_value（与 §2.3 一致）；二者由【build_diff 字段冲突产出点】写入，前端不再推断
{ type: "字段冲突", record_id, field: "箱号" | "封号", new_value, 客户编码, 箱号, 文件值:{班列号,口岸,发班时间,箱属,封号}, 库内值:{train,port,dep,box,seal,owner,dest,suffix}, 说明 }
// 产出方式：生产 _alert(atype, row, db, msg, dest_suggest="") 签名无 field/new_value 参数，字段冲突产出点需显式补——可扩展 _alert 签名，或产出后 a["field"]="箱号"|"封号"。
// new_value 取值（关键，易踩坑）：统一从 row 顶层取——field=="箱号" → row["箱号"]（生产 _alert 顶层已设 箱号 键）；field=="封号" → row["封号"]。对称取法，opencode 无需记"箱号走 row、封号走 文件值"的不对称规则。
//   ⚠ 严禁 a["new_value"]=文件值["箱号"]：生产 _alert 的 文件值 字典仅含 (班列号,口岸,发班时间,箱属,封号)，【不含箱号键】，取 文件值["箱号"] 会得到 None，导致箱号确认覆盖时把库内箱号清空。（封号也从 row 取，勿走 文件值["封号"] 以保持对称。）
// old 值无需携带在 alert 上（apply 端从库 fetch，见改动四 §4.3）。

// 弱提示（改动一）：非阻断，仅"已知悉"后从列表消失
// 同一 班列号+code_core 下多箱/多后缀可能有多行 → 生成时按 key 聚合为【一条】alert，避免重复与 confirmedWeak 误覆盖
{ type: "弱提示", key: `${train_no}:${code_core}`, 说明 }

// 缺班列号（改动一 §1.5）：数据丢失防护
{ type: "缺班列号", key: `${row_index}`, 说明 }

// 后缀变更（既有，沿用现有 _alert 产出结构）：确认后写库
// 关键键：客户编码=新客编(文件值)，目的站建议=新目的站，库内值.dest=旧目的站，库内值.suffix=旧后缀
// _doApply 组装 suffix_change 时从此 alert 读取 new_code/目的站（见 §4.3）
{ type: "后缀变更", record_id, 客户编码, 箱号, 文件值:{...}, 库内值:{dest, suffix, ...}, 说明, 目的站建议 }

// 陌生客编（既有）：阻断类报警
{ type: "陌生客编", record_id, 说明 }
```

### 8.2 确认映射结构
前端勾选后写入的确认映射：

```js
// —— 前端确认映射（用户勾选时写入）——
// confirmedSuffix 仅承担"是否勾选"标记（布尔）；组装 alerts_applied 时，new_code/目的站 从对应「后缀变更」原始 alert 读取（见 §4.3 / §8.1）
confirmedSuffix[record_id] = true                                   // 后缀变更：仅标记"已勾选"，不存数据
confirmedFieldFix[record_id + ":" + field] = { field, new_value }   // 字段冲突：键必须含 field，否则同记录箱号+封号互相覆盖；field/new_value 直接取 alert 的 a.field / a.new_value（前端不再推断、不再"供给"）
confirmedWeak[key] = true                                           // 弱提示：仅标记已知悉，不写库（key = 班列号:code_core，已聚合去重）

// —— alerts_applied 条目（_doApply 汇总生成，apply_diff 消费）——
// 字段冲突：field/new_value 源自原始 alert 顶层（a.field / a.new_value，由 build_diff 字段冲突产出点写入），经 confirmedFieldFix 透传，沿用现有 apply_diff 的 field/new_value 通道
{ source: "field_fix",     record_id, field: "箱号" | "封号", new_value }   // 写 箱号/封号 列
// 后缀变更：new_code/目的站 取自对应「后缀变更」原始 alert（见 §4.3），沿用现有 apply_diff 的 new_code/目的站 通道
{ source: "suffix_change", record_id, new_code, 目的站 }                  // new_code→客户编码 列，目的站→目的站 列（二者可同时有）
```

### 8.3 约束
- **白名单分通道、服务端强制**（见改动二 §2.3）：`field_fix` 通道 → `field ∈ ("箱号","封号")`（直接拼入 `UPDATE ... SET "<field>"`，故必须白名单）；`suffix_change` 通道 → 写入列为 `客户编码`（来自 `new_code`）与 `目的站`（来自 `目的站`），白名单校验这两列名合法（**后缀变更沿用现有 `apply_diff`/`_doApply('alerts')` 既有口径**：本项目后缀变更即改 `客户编码`、伴随更新 `目的站`；若生产代码实际列名与此不符，**opencode 以实际列名为准并同步修正本白名单**，不得因白名单写死而误拦合法列）。白名单校验**必须在后端 `apply_diff` 内执行**，即使值来自前端提交的 `confirmedFieldFix`/`confirmedSuffix` 负载，拼 SQL / 定列前也须于服务端重新校验，**绝不直接信任客户端传入值**。
- **`confirmedFieldFix` 必须用 `record_id + ":" + field` 作键**——同一记录同时有箱号与封号冲突时，若只用 `record_id` 作键，后写入的会覆盖先写入的，导致一条冲突被吞掉。
- **弱提示 `key` 唯一性**：`key = 班列号 + ":" + code_core`；生成时按该 key **聚合去重为一条 alert**（同一客户多箱/多后缀只出一条），`confirmedWeak[key]` 标记整组、移除时也按该 key 精确删一条，不会误伤其它。缺班列号 `key = 行号`（天然唯一）。
