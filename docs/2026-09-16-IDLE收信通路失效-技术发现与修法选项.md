# IDLE 收信通路失效 —— 技术发现与修法选项

> 日期：2026-09-16 ｜ 编写：芙蕾雅 ｜ 状态：**发现，未做任何代码改动**
> 触发问题（洋）：*"离重新启用「更新/作废/【草单更新】」还差一个环节，就是 IDLE 是否能很快地转、不用等。如果需要等，同事可能会因为下面公司马上就想要，而进行手动转发。这个时候如果没做判断，那'更新'的判断也是假的。"*
>
> **结论先说**：这条链路现在**不是"要等"，而是"根本转不了"** —— 会在上线后一封邮件都不转发。

---

## 1. 已实测的问题（P0，阻塞上线）

### 1.1 代码事实

`mailbots_next/core/ingest.py:325-338`：

```python
def _idle_once(self, conn, folder_name, folder_utf7):
    conn.idle()                                    # ← 328 行，在 try 之外
    try:
        conn.idle_check(timeout=self.max_idle)     # ← 330
    except Exception as e:
        _log.debug(...)
    finally:
        try:
            conn.idle_done()                       # ← 335
        except Exception as e:
            _log.debug(...)
    self._process_new_messages(conn, folder_name, folder_utf7)
```

### 1.2 实测证据（三项，均为实跑）

| # | 检查 | 结果 |
|---|---|---|
| 1 | `python -c "import imaplib; print(hasattr(imaplib.IMAP4,'idle'))"` | **False**（Python 3.13.14，本机两个解释器一致） |
| 2 | `'idle' in imaplib.Commands` / 源码 grep `idle` | **False** / 源码**无** idle 实现 |
| 3 | 实连 `imap.qiye.aliyun.com` 调 `M.idle()` | 服务端 CAPABILITY **确含 IDLE**，但客户端抛 **`AttributeError: Unknown IMAP4 command: 'idle'`** |

服务端能力（实读）：

```
IMAP4REV1 IDLE XLIST UIDPLUS ID SASL-IR AUTH=XOAUTH AUTH=XOAUTH2 AUTH=EXTERNAL
```

⇒ **服务端支持 IDLE，是客户端的 Python 标准库不支持。**

### 1.3 仓库内没有任何替代实现

- 全仓 `def idle` = **0 处**（只有 `tests/test_p1_coverage.py:875` 的 mock `conn.idle_check.side_effect`）
- 无 `imaplib.Commands` 注入 / 无 monkeypatch 垫片
- `mailbots_next/requirements.txt` 只有 **flask + openpyxl**（无 `imapclient` / `aioimaplib`）

### 1.4 上线后的真实行为

`conn.idle()` 位于 `try` **之外** → `AttributeError` 冒泡到 `_idle_loop` 的 `except Exception` → 记一行 `[{account}] IDLE error: …` → `time.sleep(10)` → 重连 → **死循环**。

- 拓扑：`IDLE_PER_FOLDER` 默认 True ⇒ **20 条连接（5 文件夹 × 4 账号）** 全部进入该循环（`serve.py:418-454`）
- 结果：**一封邮件都不会被处理**，只有错误日志在滚（约每 10 秒 × 20 条）
- **IDLE 是唯一收信通路**：`serve.py:779 start_idle_processors()`；另一个 127.0.0.1 上的 `POST /internal/forward` 只是 **error_queue 的人工补发接口**（按 `error_id` 重放已存原文），不接收新邮件。

### 1.5 为什么一直没暴露

1. **测试全 mock**：所有用例都 `patch("…imaplib.IMAP4_SSL")`，MagicMock 让 `idle()` "存在" ⇒ **套件全绿掩盖了"方法根本不存在"**。
2. **日志全是测试产物**：`mailbots_next/logs/*.log` 9 个文件里，IDLE 相关只有成对的 `Started N IDLE connections` / `All IDLE connections stopped`、`TEST MODE: skip actual send/write`、`WeCom client not available` ⇒ **IDLE 从未真跑过**。

## 2. 修法选项（请洋拍板）

### 方案 A —— 改走轮询（推荐）

**代码里已经有这条路，只是从未启用**：`Idler.poll_fallback_secs > 0` 时，`_idle_loop` 走的是

```python
while not self._stop.is_set():
    self._process_new_messages(conn, folder_name, folder_utf7)   # SEARCH UNSEEN
    time.sleep(self.poll_fallback_secs)
```

—— **完全不调用 IDLE**，连接常驻、不重连。

| | |
|---|---|
| 现状 | `poll_fallback_secs` 被硬编码为 **0**（`serve.py:448`、`ingest.py:403`），**且零测试覆盖** |
| 改动量 | 小：加一个配置项（建议 `INGEST_POLL_SEC`，默认 20~30），传入 Idler |
| 延迟 | **最坏 = N 秒、平均 N/2**，完全可预测（N=30 时平均 15 秒） |
| 负载 | 20 条常驻连接，每 N 秒各一次 `SEARCH UNSEEN`（很轻） |
| 额外收益 | **不依赖服务端推送可靠性** —— 天然规避"IDLE 断了没人知道"这类静默失效 |

### 方案 B —— 引入 `imapclient` 做真 IDLE

真推送、秒级。代价：新增依赖 + 生产机 pip 安装 + 改造 `Idler`。**建议作为后续优化**（等 A 先稳住）。

### 方案 C —— 手写 IDLE

`conn.send(b'IDLE\r\n')` + `readline()`，不加依赖，但要自己处理续行/超时/断线/`DONE`，风险中等。

### 无论选哪个，都要一起做的两件事

1. **`conn.idle()` 移入 `try`**（或修好后确认无异常路径），避免"异常 → 重连循环"这种放大故障的模式。
2. **上线自检加两条**：日志里**没有** `IDLE error: Unknown IMAP4 command`；**确有** `Email received` 与转发成功记录。

## 3. ⚠️ 但"改用轮询/修好 IDLE"**并不足以**重新启用「更新/作废」

洋列的这一个前置条件（时延）是必要的，但还有两件，缺任一件「更新」判定依然是假的。

### 3.1 判定地基现在根本不存在：台账**只有读、没有写**

- `draft.py:94-113 _get_draft_nums()` **只读** `SELECT code_num FROM forwarded_drafts`
- **全仓唯一的建表/写入在测试夹具里**：`tests/test_core.py:608-610`
- 本地 `mailbots_next/data/draft_nums.db` = **0 字节**；真实日志里反复出现
  `Failed to load draft nums: OperationalError: no such table: forwarded_drafts`（`logs/mailbot_2026-09-09.log` 几十条）

两个后果：

| 后果 | 说明 |
|---|---|
| `draft_category` **恒为 A** | `serve.py:372` 的 B 分支永不命中 ⇒ 企微"草单更新"通知**永远不会发** |
| **每封草单触发一次告警** | `_get_draft_nums` 的 `except` 里调了 `send_program_error` ⇒ **上线即 ERROR + 企微程序告警刷屏** |

而且判定规则 `draft.py:35`：

```python
category = "B" if code_num and code_num in self._get_draft_nums() else "A"
```

**与老系统 `Draft_Forward_Robot.py:311` 同构** —— 只看"这票转过没"，**完全不看内容变没变**。这就是实测 35%（6/17）纯重复误标的同一个规则。

⇒ 要重新启用标记，必须把台账升级为**版本指纹台账**：

```
draft_versions(code_num, doc_type, content_fingerprint, first_forwarded_at, sent_by, ...)
  · 索引跨 4 账号共享（同一票更新会落在不同同事邮箱）
  · 判定：有历史 且 指纹不同 → 才允许判「更新」
          有历史 且 指纹相同 → 必须退化为 A，不打任何更新/作废字样
          无历史            → A
```

### 3.2 人工转发对机器人**完全不可见**（这才是"更新是假的"的**根因**）

- 新系统**不监控任何「已发送/发件箱」**（grep = 0 条），也没有人工转发的记录入口。
- 机器人对"客户手上是什么版本"的认知，**只包含它自己发过的**。

⇒ **哪怕 IDLE 快到 1 秒，只要发生过人工转发（同事着急、机器人停机、网络断、或 IDLE 坏掉），「更新」在语义上就不成立。** 时延只是"人工转发会不会发生"的一个诱因，不是根因。

**修法方向（三选一或组合）**

| | 做法 | 代价 |
|---|---|---|
| (a) | **给人工转发可见性**：把「已发送」纳入只读轮询，识别"同事手工发给客户"的邮件 → 记进版本台账 | 多 4 条连接；需能区分"机器人自己发的"与"人工发的"（机器人发出的可加自身指纹）；**需先实测阿里云 SMTP 发信是否会落到「已发送」** |
| (b) | **弱化语义**：不声称"此前版本作废"，只陈述事实（附本版时间戳） | 最省事，但失去了"更新"的提示价值 |
| (c) | **保守标注**：仅当"上一版由机器人发出 + 指纹不同 + 距上次发出 ≥ N 分钟"才标「更新」，否则只发不标 | 与"宁可漏标、绝不误标"一致 |

**建议 (a) + (c) 组合。**

## 4. ⚠️ 另一个边界：收信发现依赖 `UNSEEN`

`ingest.py:255-257`：

```python
criteria = f'(UNSEEN SINCE {imap_since(self.forward_since)})' if self.forward_since else "UNSEEN"
```

同事**手动转发前必然会先打开邮件**（= 标 `\Seen`）。若一封邮件的 **4 个账号副本都被读掉**，机器人的 `UNSEEN` 搜索就**整封跳过** —— 注意这时不是"误标"，而是**彻底漏发**（与 `CQWLJT260912004-D` 那次静默丢信同类）。

- 有 4 份副本可捡，故概率中低；
- 但它意味着**"同事先读了邮件"这件事会同时影响两条路径**，值得在设计里一并处理。

实测各文件夹未读积压（`maoxiaoyang` 账号）：运单草单 58 封/未读 0；运单号 50/0；DSK 9/0；ATB 15/0；Tracing 715/0。

## 5. 附带核实：IDLE 的拓扑与"会不会等"（供设计参考）

| 事实 | 值 | 出处 |
|---|---|---|
| 连接拓扑 | 每 (文件夹 × 账号) 一条 = **20 条** | `settings.py:55` `IDLE_PER_FOLDER` 默认 True |
| 设计意图 | "没有任何文件夹会排在另一个文件夹的 29 分钟 `idle_check` 后面" | `serve.py:419-421` docstring |
| IDLE 重发间隔 | `MAX_IDLE_SEC = 1740`（29 分钟，符合 RFC 2177） | `settings.py:57` |
| 兜底重扫 | 每次 `idle_check` 返回（含超时）后都跑一次 `_process_new_messages` ⇒ 推送丢失最长等 29 分钟 | `ingest.py:338` |
| 轮询兜底 | `poll_fallback_secs = 0` ⇒ 当前**纯 IDLE、无兜底** | `serve.py:448` |
| 防抖/延迟发送 | **全仓 0 处**（无"等一等看有没有新版本"的逻辑） | grep `debounce\|延迟\|grace\|DELAY` |
| 同步处理 | 处理在 IDLE 线程内完成，期间该文件夹 IDLE 未重新武装 ⇒ 小盲窗（≈批量耗时） | `ingest.py:315/338` |

> 补充：IDLE 路径取信用 `conn.fetch(uid, "(RFC822)")`（`ingest.py:277`），`fetch_raw_by_uid` 也用 `(RFC822)`（`:365`）。⇒ **Q1（`RFC822` 是否隐式置 `\Seen`）不只影响退信轮询，也影响主收信路径**，建议与本次修复一并处理（改 `BODY.PEEK`）。
