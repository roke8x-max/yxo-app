## 1. 终局目标：把「顺手」翻译成能验收的话

「顺手」不是一个技术词。为了避免执行方各自理解，本文把它拆成四个可判断的状态：

| 状态 | 含义 | 今天是否满足 |
|---|---|---|
| **改得动** | 想改一个功能，能在 5 分钟内定位到该改哪个文件的哪一段 | ❌ 前端是一个 2754 行的大文件；后端是 1676 行的大文件 |
| **看得见** | 出问题时，日志里能看到「哪个环节、什么原因」，而不是静默跳过 | ❌ 主站 30 处 `except Exception`，其中 22 处静默吞掉 |
| **坏不了** | 改完之后，一条命令就能告诉我「有没有弄坏原来能用的功能」 | ❌ 主站后端**只有 1 个测试文件**，且只测权限 |
| **恢复得了** | 出事能退回上一版，且**数据也能恢复** | ⚠️ 代码能回滚，**数据库不回滚** |

### 1.1 澄清一个被反复误解的目标

**「把前端和后端拆开」不是目标，也不需要作为目标。**

理由（实测，见 §3）：主站**其实已经是**「后端返回 JSON + 前端用 JS 取数据」的形态了——59 条路由绝大多数返回 JSON，4 个页面里几乎没有模板变量（基本是静态空壳）。真正缺的再往前一步（独立的前端工程、独立域名、引入 Vue/React + 打包工具）解决的是**多人协作与独立部署**，对「一个人内网用」的场景**收益最低、成本最高**。

所以：**把这个目标从「分离」改成「结构化」**——前端按模块分文件，后端按业务域分文件。这才对得上「改得动」这个判据。

## 2. 约束（任何方案不得越过）

1. **人**：一个人维护，业务部门出身，不是专业开发。→ 方案必须能在**碎片时间、中断后能捡起来**的粒度上推进。
2. **数据**：客户名 / 收发货人 / 运价 / 提单号属敏感数据。→ 不出内网、不进第三方 LLM、不入公开仓库。生产真源是服务器上的 SQLite，**不是**任何云服务。
3. **拓扑**：内网 nginx 反代（`http://<内网>:5000/yxo/`）；本机是开发库，生产在服务器 `D:\YXO_DATA\yxo_app`，**只从 `main` 拉**。
4. **三大支柱边界**（动之前先认清自己在动哪一根）：

   | 支柱 | 代码落点 | 现在能不能动 |
   |---|---|---|
   | 邮件机器人（自动入口） | `mailbots_next/`（新，主线）；`mailbots/`（旧，**生产仍 live**） | 新：可改。旧：**只修 bug，绝不加新功能** |
   | 主站（数据平台，:5011） | `app.py` / `admin_api.py` / `templates/` / `static/` / `manifest_engine.py` | **本路线图的主战场** |
   | 企微机器人（人机协同，:5001） | `wecombot/` | ⚠️ 生产真源在服务器 `D:\YXO_DATA\WeComBot`，**独立、不随 git 更新**，改动前必须先同步回来 |

5. **工作流铁律**（继承自 `AGENTS.md`，不得绕过）：
   - 只用 `main`；每次改动从 `main` 拉**扁平命名**的临时分支（**不带斜杠**）→ PR → `main`。
   - **不得自行 commit / push**，由毛骁洋执行。
   - 用 `git add <具体文件>`，**禁止 `git add -A`**。
   - 一次 PR 只做一件事。
   - 报告必须附**实跑证据**（命令 + 输出末几行 + 文件:行号）。禁止「已证实」「应该没问题」。
   - **禁止为了让测试变绿而放宽业务判据**（改正则、改阈值、改分类规则）。测试红 → 先证明是数据问题还是逻辑问题。

## 3. 现状事实基线（实测，执行方直接引用）

### 3.1 后端体量与结构问题

| 文件 | 行数 | 路由 | `.execute()` | `get_db()` | 手工 commit/close | `except Exception` | 其中静默吞掉 |
|---|---|---|---|---|---|---|---|
| `app.py` | **1676** | 36 | **79** | **36** | 21 / 40 | **30** | **22** |
| `admin_api.py` | 1149 | 18 | 21 | 0 | 5 / 8 | 28 | 24 |
| `manifest_engine.py` | 981 | 0 | 32 | 0 | 0 / 2 | 4 | 4 |
| `import_excel.py` | 259 | 0 | 6 | 0 | 1 / 3 | 5 | 4 |

- `app.py` 里**建表与迁移 SQL、计价逻辑、HTTP 路由**同处一个文件。
- 数据访问只有**半层** DAO：唯一的 DAO 是 `data/records_dao.py`（约 100 行），**只管 `records` 的读**；写路径全部裸 SQL 散落在路由里，连接由路由自己开、自己 commit、自己 close。
- 正面事实（不要改坏）：SQL **全部参数化**，无拼接注入；公司范围过滤已有真 DAO。

### 3.2 前端结构问题

| 文件 | 行数 | 大小 | 内联 `<script>` | 请求包装 `_origFetch` 复制份数 |
|---|---|---|---|---|
| `static/app.js` | **2754** | 128 KB | 0 | 3 |
| `templates/admin.html` | — | 45 KB | 1 | 4 |
| `templates/manifest.html` | — | 41 KB | 1 | 0 |
| `templates/tuoshu.html` | — | 20 KB | 1 | 4 |
| `templates/index.html` | — | 10 KB | 0 | 0 |

- `static/app.js` 内共 **25 处 `fetch(`**；「统一带 CSRF、统一错误提示」的那段包装被**复制在 3 个文件里共 11 份**。
- 全仓**没有 `package.json`、没有任何构建工具**（Vite / webpack 均无），也没有前端框架。
- **这既是问题也是资产**：没有构建链 = 改完刷新浏览器就生效，没有编译这一步。本路线图**保留这个性质**。

### 3.3 测试分布（关键：护盾几乎只装在两个地方，主站是裸的）

| 区域 | 测试文件 | 用例数 |
|---|---|---|
| `mailbots_next/tests/` | 22 | **323** |
| `mailbots/tests/`（旧系统） | 23 | 165 |
| `tests/`（**仓库根的、主站的**） | **1** | **32** |
| **合计** | 46 | 520 |

- **主站（`app.py` / `admin_api.py`）只有一个测试文件 `tests/auth_gate_test.py`，32 个用例全部是权限门禁矩阵。**
- 天天在用的路径——**Excel 导入、舱单导入、算价、导出、托书、回收站、字段维护——没有任何测试**。
- 已知缺陷：`.gitignore:72` 有一条裸规则 `test_*.py`，只在 `.gitignore:74` 为 `mailbots_next/tests/` 开了例外。→ **在主站或其他任何地方新建测试文件会被 git 静默忽略、永远不会进版本库。**

### 3.4 「生产」与「仓库」不是同一份代码（实测，非推测）

以下为 2026-10-04 对 `10.0.199.184` 的只读 HTTP 探测结果：

| 探测 | 结果 | 含义 |
|---|---|---|
| 5011 上 `/api/csrf`、`/api/login`、`/api/auth_meta` | **全部 404** | 权限模块（RBAC v2.5 + 游客 + A/B/D4）**至今未部署到生产**；`docs/superpowers/specs/2026-09-30-deploy-handoff-combined.md` 未执行 |
| 5001 上 `/api/notify` | **405**（存在，只收 POST） | 生产企微**有**仓库 `wecombot/` 里没有的接口——版本漂移实锤 |
| 端口 445 / 5011 / 5001 | 通（需开 ZeroTier） | 22 / 3389 / 5021 / 5022 不通 |
| SMB 共享盘 | `Access is denied` | 能连到 445，但缺共享盘凭据，**读不到** `D:\YXO_DATA` |

**推论（写进约束）**：任何「改完之后上生产」的动作，都必须先核实**生产当前实际跑的是哪一版**，不能假设「仓库 = 生产」。

### 3.5 构建/部署链的缺口

- 无 CI（全仓无 `.github`）。
- `scripts/hooks/pre-push`（拦直推 main）与 `scripts/install-hooks.ps1` 存在，但**本机 `.git/hooks` 实测一个钩子都没装**。
- `start.bat` 与 `requirements.txt` 只装 `flask` + `openpyxl`，而 `app.py` 实际还依赖 `admin_api` / `data.records_dao` / `auth` 等——**新机器照 `start.bat` 装可能起不来**。

## 4. 为什么是这个顺序（排序逻辑，执行方必须理解，否则会做错）

毛骁洋的原话是「要改代码太麻烦，而且已经逐渐有牵一发动全身的感觉」。**这句话是症状，不是需求。**

- 症状：动一处，心里没底会不会碰坏别处。
- 病因：**没有任何东西能在你改完之后告诉你「你弄坏了 A 功能」**。
- 结论：**先装护盾，再动结构。** 顺序反了会发生三件事：
  1. 拆前端时把某个页面弄坏，几天后业务上才被发现；
  2. 拆后端时把某个接口的参数改名，前端静默失效；
  3. 反复「重构 → 出问题 → 回滚」，最后得出「重构很危险、还是别动」的结论——**这就是现在卡住的真正原因**。

> 因此：**第 1 阶段（补测试）不做任何结构改动，也不要「顺手」修 bug。** 它的产出只有一个——一条能报警的命令。

## 5. 路线图

> 每一阶段都是**可独立交付、可独立验收、随时可停**的。停在任何一阶段，项目都比开始前更好。

### 阶段 0 · 基线冻结（半天到一天）

**目的**：让后面每一步都有「改之前是什么样」的参照。

**做什么**
1. 确定并**记录**本机唯一解释器（自检 `sys.executable` 并写进报告）。
2. 修好依赖清单：让 `requirements-dev.txt` / `requirements.txt` 能一次装齐，跑得起测试。
3. 跑通现有全套测试，**记录真实数字**（收集数 / 通过数 / 失败数），不要用文档里的旧数字。
4. 修 `.gitignore:72` 的裸 `test_*.py` 规则（改为精确忽略，或按目录开例外），使**新测试文件能进版本库**。
5. 把「生产实际跑的是哪一版」核实清楚并记录（见 §3.4 的方法）。

**不做什么**：不写业务代码、不修 bug、不拆文件。**发现的问题只登记，不改。**

**验收**：一条命令（写进文档）能在本机跑出「0 failed」，并给出用例总数。

**停止条件**：命令能跑、数字记录下来即可停。

---

### 阶段 1 · 安全带：给「天天用」的路径装报警器

**目的**：把「改完心里没底」变成「改完跑一条命令就知道」。

**选点原则**（重要，执行方按此自己选，不要贪多）
- 优先**写路径**（会改数据的），其次读路径；
- 优先**改坏了业务立刻受影响**的；
- 优先**现在完全没测试**的；
- 先挑 **3～5 个**，做完再谈下一批。

**候选清单**（按推荐顺序）
1. Excel 导入（`import_excel.run_import`）
2. 舱单导入（`manifest_engine.py`）
3. 算价（`compute_price` 及莫斯科/明斯克回退）
4. 导出 / 托书（`tuoshu_engine.py`）
5. 回收站软删与恢复（`/api/trash*`）

**手法**
- 用 Flask 自带的测试客户端（`test_client()`）打接口，**不要**为了测试去改业务代码。
- 测试必须用**临时数据库**，严禁连生产库。参考 `mailbots_next/tests/conftest.py` 已经跑通的隔离做法。
- 每条测试要能**真的报警**：即「把这段业务代码故意改坏，这条测试必须失败」。这是本项目已确立的「真锁」文化，必须延续。

**不做什么**：不追求覆盖率数字、不为测试重构业务、不引入新的测试框架。

**验收**：每个选点至少有 1 条「真锁」测试；把「改坏 → 变红 → 改回 → 变绿」的过程作为证据贴出。

**停止条件**：选点覆盖完即停。

---

### 阶段 2 · 前端拆骨（零后端风险，先做能立刻见手感的一步）

**目的**：让「改界面」不再是在 2754 行里翻找。

**做什么**（顺序即推荐执行顺序）
1. **抽出唯一的请求层**：把复制在 3 个文件里的 11 份「包装 fetch」合并成 1 个文件，统一负责 CSRF 头、错误提示、加载状态。**这一步收益最大、风险最低。**
2. **把三个页面的内联 `<script>` 搬成独立文件**（`admin.html` / `manifest.html` / `tuoshu.html`）。
3. **把 `app.js` 按功能切成若干文件**，用浏览器原生 ES module（`<script type="module">`）组织。**一次只搬一块，搬完立刻在浏览器里点一遍。**

**硬约束**
- **不引入 npm / 打包工具 / 前端框架**。原生 ES module 浏览器直接支持，改完刷新即生效——这个性质要保住。
- **后端一行都不改**。接口路径、参数、返回结构保持完全一致。
- 每一小步都要能在浏览器里肉眼验证；前端没有自动化测试，**人工核对清单就是这一阶段的验收工具**。

**验收**：逐项核对「拆分前能做的事，拆分后全都能做」；给出核对清单（页面 → 功能 → 结果）。

**停止条件**：文件切分与请求层合并完成即停。**不要顺手改样式、不要顺手改交互。**

---

### 阶段 3 · 后端分域（一次一个域，爆炸半径可控）

**目的**：让「改一处」的影响范围可以预测。

**做什么**
1. 用 Flask 自带的 **Blueprint** 机制，按业务域把 `app.py` 拆开。推荐域划分：订舱主表 / 舱单 / 托书 / 价格 / 回收站 / 字段与选项维护 / 权限。
2. **先拆最独立、使用最少的域**（如回收站、字段维护），**最后拆主表**。
3. 每拆一个域：跑阶段 1 的测试 → 手工冒烟 → 提交 → 再拆下一个。

**关键纪律**
- **先只做「路由搬家」，不动数据访问。** 一个 PR 里不要同时搬家又改 SQL——那是两件事。
- 拆分前后要能证明「路由一条不多、一条不少」。可写一个脚本 dump `app.url_map` 对比，这是可以自动化的。
- 不换框架（保持 Flask）。

**验收**：路由清单逐条对应；阶段 1 的测试全绿；主页面手工冒烟通过。

**停止条件**：拆到「新增一个业务域不再需要动 `app.py`」即可停，不必追求拆干净。

---

### 阶段 4 · 数据访问收口

**目的**：消灭「手工开连接、忘记 commit、忘记 close」。

**做什么**
1. 把**写路径**也纳入 DAO（现在是半层），让路由不再直接写 SQL。
2. 统一连接生命周期（`app.py` 已在用 Flask 的 `g`，顺着它做，不要另起一套）。
3. 连接与事务的边界写进文档，新代码照办。

**硬约束**
- **绝不改 `yxo.db` 的表或列结构**（含「开票子公司名称」列名）。
- **绝不碰「退舱」记录的语义**——它是业务凭据，只读、永不删除、永不被覆盖。
- 改数据库访问之前**先备份**。

**验收**：给出可执行的统计命令，证明 `app.py` 里的裸 `.execute()` 数量降到可解释的少数；测试全绿。

**停止条件**：写路径都过 DAO 即停。

---

### 阶段 5 · 可靠性收尾（按需，不必一次做完）

**目的**：把「出问题能恢复」这条判据补齐。

**做什么**（按价值排序）
1. **数据库定时备份 + 演练一次真实恢复**。这是当前**最大的单点**：代码能回滚，数据回滚不了，而现在全靠人工记得备份。**光有备份脚本不算完成，必须真的恢复一次并验证数据完整。**
2. 把「静默失败」收敛到**会影响业务判定**的那些（例如「无路由就跳过」这类必须留痕的），**不要**为了消灭 `except: pass` 去改正常代码（幂等迁移、资源清理、`KeyboardInterrupt` 属于正常写法）。
3. 对齐依赖清单与启动方式，让新机器能一次装好、一次启动。
4. 生产与仓库的漂移收取：把服务器上的真实版本（如企微的 `/api/notify`）同步回仓库，或明确标注为「独立于 git、勿以仓库为准」。

**验收**：恢复演练有完整记录（备份文件 → 恢复命令 → 恢复后数据核对结果）。

## 6. 明确不做的事（anti-goals）

以下每一项都会被 AI 智能体「顺手」提出来。**未经毛骁洋明确同意，一律不做**，理由已给：

| 不做 | 为什么 |
|---|---|
| 引入 Vue / React / 构建工具 / 独立前端工程 | 解决的是多人协作与独立部署；一个人内网用，收益最低、成本最高，且会**增加**「改代码麻烦」的程度 |
| 依赖 `npm` 的工具链 | 会让「改一行刷新浏览器」变成「改一行先构建」，把现有最大的便利丢掉 |
| 重写主站 / 换框架 | 「先止血再重构」是本项目已确立的原则；整体重写会同时失去护盾和可用性 |
| 动 `yxo.db` 表结构、改「开票子公司名称」列名 | 项目已有铁律；下游多个机器人依赖 |
| 以任何方式删除/软删/覆盖「退舱」记录 | 业务凭据，遇到必须先问毛骁洋 |
| 在旧 `mailbots/` 上实现新功能 | 旧系统只修 bug；新功能一律写 `mailbots_next/` |
| 「顺手」修改与本次无关的代码 | 爆炸半径不可控，是「牵一发动全身」的成因之一 |
| 为了让测试变绿而放宽业务判据 | 项目有血泪史：放松判据会让测试变绿，但悄悄放松生产判定门槛 |
| 追求测试覆盖率数字 | 判据是「改坏了会不会报警」，不是百分比 |
| 自行 `git commit` / `push` / `git add -A` | 毛骁洋握 git 拍板权 |

**什么情况下才重新讨论前端框架**（触发条件，写下来免得反复纠结）：
页面数量明显增长（超过 8 个）、或出现需要跨页面共享复杂状态的交互、或**有第二个人要接手维护**——三条中任意一条成立时，再单独评估。

## 7. 给执行智能体的硬约束（每次开工前读一遍）

1. **一次只推一个阶段的一小步。** 做完停下、报告、等验收，**不要自行推进下一阶段**。
2. **不许自行 `commit` / `push`。** 用 `git add <具体文件>`，禁止 `git add -A`。
3. 分支名用**扁平命名、不带斜杠**（如 `fix-frontend-request-layer`），从 `main` 拉。带斜杠的分支在本机会**假报成功但 ref 没落盘**，进而让 `git status` 把整仓文件显示成新增。
4. **不要相信本地 `git status` 的 ahead/gone 数字**——本机杀软会导致 ref 缓存陈旧；核实远端一律用 `git ls-remote origin`。
5. **报告必须自带证据**：实跑命令 + 输出末几行 + `文件:行号`。禁止「已证实」「应该没问题」「理论上」。
6. **测试红了先定性**：是数据问题、环境问题，还是逻辑问题。**绝不用「放宽判据」的方式绕过。**
7. **改之前先说清楚「要改哪几个文件、为什么」**，改完给「怎么验证」。
8. **不确定就停下来问**，不要替毛骁洋拍板。发现计划外的问题**只登记，不顺手修**。
9. **碰生产相关的事（部署、数据库、服务器文件）一律先出方案等拍板**，并先备份。
10. 本文档与 `AGENTS.md` 冲突时，**以 `AGENTS.md` 为准**并立即报告冲突。

## 8. 怎么验收（给毛骁洋的「一句话验收」）

每个阶段只给你一个动作，做完这个动作就知道这一步成没成：

| 阶段 | 你只需要做这一个动作 |
|---|---|
| 0 · 基线 | 让智能体在你面前跑那条测试命令，看它输出「0 failed」和一个数字 |
| 1 · 安全带 | 让智能体当着你的面**故意改坏一处业务代码**，看测试是否**立刻变红**；再改回去，看是否变绿 |

| 4 · 数据访问 | 让智能体给你看那条统计命令的前后对比数字 |
| 5 · 可靠性 | 让智能体**真的恢复一次备份**给你看，而不是告诉你「备份脚本没问题」 |
