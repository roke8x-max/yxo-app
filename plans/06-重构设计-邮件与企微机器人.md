## 1. 入 git 思路：现在同步，不要等完全重构

### 1.1 结论（推荐）

**现在就把下午的修复 + WeComBot 初始捕获同步进 git（dev），重构作为独立的设计+实施阶段在基线之上做。** 理由：

1. **生产现在跑在未版本化的修复代码上**（`D:\YXO_DATA\MailBots` 今天改的，不在 git）。一旦该目录磁盘损坏/误删，修复丢失。先入 git = 买保险。
2. **重构应从"修好的基线"起步**，不是从 8/8 的 bug 版。若先重构再提交，等于在带 bug 的旧基线上重做，可能把 `box` 那个坑再带回来。
3. **重构是大设计工程**，本回合你只要"思路 + 设计"，落地要排期。期间生产修复不能裸奔。
4. 你原话"等以后 n8n 搞好了就顺畅了"——说明重构/CI 是未来态，当下先把代码安全地收进仓库。

### 1.6 git pull 的删除语义（q-0 澄清）

重构后若删除旧文件，`git pull` **只删 git 跟踪清单里的文件**，不影响其他：
- ✅ **会删**：被 `git rm` 的旧代码文件（如废弃的 `Old_Robot.py`）→ 正是你要的清理。
- ❌ **不会删**：`.gitignore` 里的本地数据/配置（`*.db`、`logs/`、`config_local.py`、`secrets.json`）→ 安全，pull 碰不到。
- ❌ **不会删**：git 树**之外**的旧目录（如 `D:\YXO_DATA\MailBots`）→ 需手动改名备份后删（迁移阶段做）。
- ⚠️ **绝不**用 `git clean` 做清理（会误删 untracked 本地文件，含密钥/库）。
- 一句话：git = 唯一真相，pull 按跟踪清单增删；本地私有数据与树外目录都不在它的管辖范围。

## 2. 重构设计：从需求到技术

### 2.1 需求层（为什么要重构）

| 编号 | 需求/痛点 | 来源 |
|---|---|---|
| R1 | 路由数据源分裂（bot_config / dsk_config_cache.json / records / 飞书死链），不可靠、断链 | 交接 §7.9、§7.1 |
| R2 | 异常被静默吞没，线上停摆无感知（今天两起事故同一根） | 交接 §7.19、09 复盘 |
| R3 | 明文密码硬编码、secrets 散落多模块直读 | 交接 §7.2、§7.20 |
| R4 | 去重 4 套实现、forward_since 口径不一 | 交接 §7.6、§7.7 |
| R5 | 运踪"新班列自动转发"断链（飞书死链不灌 yxo.db） | 交接 §7.1、09 §3 |
| R6 | 进程/生命周期失稳（Draft 泄漏、假守卫、start/B 回收） | 09 §4 |

| R9 | 部署靠手动，n8n/CI 未接 | 02 方案 |

### 2.2 目标架构（单一真相 + 统一层）

```
                 ┌─────────────────────────────────────────┐
   邮件IMAP ──▶  │            统一机器人框架 (core/)          │
                 │  daemon(可观测) / routing / dedup / notify│
                 └───────────────┬───────────────────────────┘
                                 │ 全部经唯一路由解析
                         ┌───────▼────────┐
                         │  yxo.db (真相)  │
                         │  records(主数据)│
                         │  bot_config     │  scope=company(To/Cc)
                         │  (company/train)│  scope=train(仅例外覆盖)
                         └────────────────┘
   企微(kf/应用) ◀── notify_by_name ──┐
   草单待确认 ◀── draft_pending ──────┘
```

**核心决策 D1：路由单一数据源 = `yxo.db`。**
- Layer2（公司→To/Cc）：保留 `bot_config scope='company'`。
- Layer1（这封邮件→哪家公司）：**全部从 `records` 推导**（Waybill/Draft 已是；Tracing 用 09 修复 B 的模式；DSK/ATB 把飞书箱号→公司改成读 `records`）。
- `scope='train'` **降级为可选覆盖层**（只放 records 里没有/需特殊路由的班列）。
- **消除** `dsk_config_cache.json`（它只是 feishu 总表→缓存的中转，feishu 退役后无意义）。
- **一举关掉 R1 + R5**：只要 `records` 有新班列，所有机器人自动推导路由，不再手工维护 train 表。

**核心决策 D2：统一路由模块 `core/routing.py`。**
`resolve_recipients(code=None, box=None, train_id=None) -> {to, cc}`，5 个机器人共用，删除各自重复的 `resolve_recipients`/`load_dsk_routing`。

**核心决策 D3：统一去重 + forward_since。**
单 `core/dedup.py`（命名空间隔离），替换 4 套；forward_since 语义统一（DSK/ATB/Tracing 补齐护栏）。

**核心决策 D4：可观测性优先（重构第一刀）。**
- `daemon_loop` 必须把 `traceback` 写进日志文件（今天卡死无日志的根因）。
- 所有"跳过/未匹配/无路由"分支打印**结构化原因**，并对"无路由跳过"发**企微告警**（避免再出现"新增班列没配就被静默漏转"）。
- 这是最高优先级——两个静默故障一天内连发，根都在"看不见"。

**核心决策 D5：Secrets 集中外置。** `config_local.py` / `secrets.json`（不入库），零硬编码密码/token。

**核心决策 D6：进程生命周期治理。**
- 单一监管（合并看门狗），**真·单实例锁**（PID 文件，非假端口守卫）。
- 调度拉起用 `pythonw` + DETACHED，避免 `start /B` 被任务树回收（09 §4.2 实证的运踪遗漏）。
- **运行模型二选一（待拍板 D7）**：
  - 方案 X（保守）：保留 `D:\YXO_DATA\MailBots` 为运行时，`deploy.ps1` 增加"git checkout → rsync 到运行时"同步步。
  - 方案 Y（干净，✅ **已确认**）：机器人直接**从 git 检出的目录运行**（生产从 main 检出的 `D:\YXO_DATA\yxo_app\mailbots`），git = 唯一真相，去掉"运行时副本"这一整类分叉。需改计划任务路径（迁移阶段做）。

**核心决策 D7（WeComBot 收尾）：**
- 入 git + 外置凭据（见 1.3，✅ 已完成首抓）。
- `:5001` 审批端点：**未来实现，并入 n8n 计划**（原规划说"已就绪"是错的，非当前刚需；等 n8n CI 自动化时再给 `server.py` 加审批/部署回调端点）。
- gate NLP 接入（R8，PIPL 合规出网）——现在接还是保留规则 parser？
- 入站消息 PII 脱敏落盘（与 gate 方向相反，需修）。
- `requirements.txt` 补 `requests`。

**核心决策 D8：Syncer 重构（喂数闭环）。**
- `Database_Syncer` 不再写飞书死链；改为维护 `records` + 必要的 `bot_config` 默认。
- 飞书退役过渡期：可读飞书总表补 `records`，但最终 `records` 由 yxo_app 业务流维护。

### 2.3 模块拆分目标（greenfield per-module）

```
yxo-app/
  mailbots/            # 5 机器人 + core 公共层
    core/              # routing / dedup / daemon / notify / config(外置)
    waybill.py  draft.py  dsk.py  atb.py  tracing.py  syncer.py
  wecombot/           # 企微机器人（外置凭据）
    server.py  cs_bot/  config_local.py
  yxo_app/            # 现有 Flask 后端（已入库）
  config/             # 跨模块 secrets 外置
  scripts/            # deploy.ps1 / seed_routing.sql / 监管
  gate/               # NLP 合规网关（接 WeComBot）
```

### 2.4 实施顺序建议（重构阶段）

1. **D4 可观测性**（先让故障可见）→ 立刻降低再次静默停摆概率。
2. **D1+D2 路由单一源**（records 推导 + `core/routing.py`）→ 关 R1/R5，根治运踪断链。
3. **D5 secrets 外置**（收尾 WeComBot 入 git 时一并做）。
4. **D3 去重/forward_since 统一**。
5. **D6 生命周期治理**（选 Y 则顺带解决运行时分叉）。
6. **D7 WeComBot 审批/gate/PII**。
7. **D8 Syncer 喂数闭环**。
