## 0. 一句话定位

渝新欧铁路货运代理的「订舱 / 运踪 / DSK / ATB 邮件协同」系统，正从「飞书多维表 + 散落 Python 脚本」走向「本地 SQLite 单一数据源 + 前后端分离 + 双 Agent 分布式开发」。本文只讲业务与方向，不含具体实现细节。

---

## 1. 业务背景

- **主体**：渝新欧铁路货运代理（cqtransit.com / yxologistics.com），做中欧班列订舱、运踪、DSK/ATB 邮件协同。
- **历史数据层**：飞书多维表（订舱总表 + 4 张按公司分工的子表）。同事按公司维护主数据 + 操作字段（箱号 / 封号 / 草单 / 报放单 / 数据状态…）。
- **自动化**：Python 脚本定时读写飞书，驱动下游——邮件机器人（DSK/ATB/运踪自动转发）、价格同步、配置同步、企微 Bot。
- **痛点**：飞书客户端卡顿（同事电脑配置一般）、API 配额 / 账号管理成本、多人并发协作弱 → 启动「去飞书化」。
- **去飞书方案**（共享盘 `优化方案_飞书依赖替换.md`）：方案 A = 本地 Flask+SQLite 轻量 Web 表格替代人工编辑层，脚本改读本地库。已有原型验证（yxo_web）。
- **运行环境**：服务器 `10.0.199.184`（助手「小叽」）7×24 跑业务；本机（你 + 助手「芙蕾雅」）做开发。
- **合规红线**：客户 PII（客户名 / 手机 / 邮箱 / 提单号 / 运价 / 身份证）不能裸奔到第三方 LLM / 外网。

---



## 2. 业务需求

1. **订舱数据维护**：同事按公司分工，在直观界面维护订舱主数据 + 操作字段；替代飞书，零重客户端、不卡。
2. **自动化协同**：邮件机器人（DSK/ATB/运踪/运单草单/运单号自动转发）、价格匹配回填、配置同步、企微通知。
3. **双 Agent 分布式开发**：本机（芙蕾雅 / 你）+ 服务器（小叽）协作；任务经 GitHub 下发，审批经企微回调，测试经 GitHub Actions。
4. **合规**：所有发往外部 LLM 的文本经脱敏 + 审计；敏感字段不落第三方。
5. **稳定性**：业务 7×24 不中断、异常自动拉起、部署可一键回滚。

### 3.2 基础设施

- 服务器 7×24 + watchdog 自愈；ZeroTier 可达但波动；企微 :5001 公网稳定；mihomo 出网（服务器自身）待部署。
- 协作流程已设计（dev→PR→main + GitHub `tasks/` 任务下发 + 企微审批 + Actions 测试）但未落地。



### 3.3 遗留问题（避坑点，非本次改造目标）

- 飞书凭据仍散落硬编码（MailBots `APP_SECRET` 等）；secrets 未外置。
- 生产 `yxo.db` 与代码同机、未隔离；前端后端未拆。
- Tools 多飞书耦合：`sync_to_subtables`/`cache_manager`/`sync_price` 飞书 I/O 已无意义；但 `match_price`（已被 yxo_app 内置 `compute_price` 取代）、`数据清洗`（已被舱单上传页取代）无需迁移。
- gate 为 openclaw 设计、现无运行调用方（无付费 LLM、opencode 自带免费模型自管路由、agent 自身推理不走它）；仅 WeComBot 未来免费模型 NLP 会启用，含跨模型 timeout fallback。PIPL 合规在「手写 LLM 调用」场景仍须闭环。

## 4. 下一步目标（方向，2026-08-10 拍板）

**总原则：不改造旧版，按现有需求分模块重新优化代码（greenfield per-module）；旧代码仅作避坑参考。**

1. **模块拆分**（统一纳入一个 GitHub 仓库 `yxo-app`）：
  - 后端 `yxo_app`：纯 API / 业务引擎（订舱委托书、舱单、价格、配置）。
  - 前端（延续 web 命名，如 `yxo_web`）：**独立前端工程**，与后端分离。**起点是 yxo_app 现有的** `templates/*.html` **+** `static/{app.js,style.css}`**（即洋设计的最新前端：index / tuoshu / manifest / admin 四页 + 130KB app.js + style.css），不是旧的 yxo_web 原型**。旧的 yxo_web 实验原型另作归档，不并入新前端。
  - `wecombot` / `mailbots` / `gate`（LLM 合规 + timeout fallback 层，**仅用于 WeComBot 免费模型 NLP 等手写 LLM 调用**；agent 自身推理、opencode 内置模型不走它）/ `config` / `scripts` / `tasks`。
2. **技术基线**：前端后端分离；生产 `yxo.db` 不入库；secrets 外置（`.example.json` 模板 + `.gitignore`）；统一仓库统纳业务代码；`deploy.ps1` 统一纳管多服务。
3. **协作落地**：双 Agent 工作流（tasks/ 下发 + 企微 :5001 审批 + GitHub Actions 测试）从设计转入实施。
4. **合规闭环**：对**手写 LLM 调用**（主要是 WeComBot 未来免费模型 NLP —— 识别自然语言、理解未设命令、收集真实需求）经 gate 脱敏 + 审计 + 跨模型 timeout fallback（一个模型申请超时切另一个免费模型）；agent 自身推理与 opencode 内置免费模型由各自框架管理，不重复套网关。
5. **落地顺序**（待逐项正确认）：① 工作流 / 分支设置 → ② 各模块改造与功能需求 → ③ GitHub 仓库重组。

### 改造方向矩阵（问题 → 改造原因 → 目标，源自《代码体检报告》）

> 把报告指出的六大维度问题逐条映射为「为什么要改（原因）」与「改到什么程度（目标）」。均为方向性描述，不含实现细节；具体方案在后续逐模块讨论中细化。优先级参考报告 §7（高：迁移机制 / 统一输入校验；中：令牌 / 逻辑抽离+单测 / 协同改进；低：日志 / 容器化 / 离线缓存）。

**A. 架构与模块化**
- **报告问题**：`app.py` 约 1300 行，业务逻辑 / 数据访问 / API 路由混在一起；计价、港口别名、发班时间联动等纯逻辑相关的代码散落在全局变量与多处函数（如 `_MOSCOW_FB`、`_MINSK_FB`）。
- **改造原因**：功能累加后可读性下降，逻辑难以定位与复用，重构时没有测试护盾，改动易引入回归。
- **改造目标**：按模块拆分（价格 / 港口 / 发班时间等纯函数独立成模块并补单元测试）；遵循「greenfield 分模块重优化、旧代码仅避坑」总原则，新代码从第一天就分层清晰。

**B. 数据层**
- **B1 Schema 演进** — 报告问题：手动 `ALTER` 易漏或顺序错位。原因：字段增多后迁移风险高、故障难恢复。目标：引入轻量迁移机制（版本表 + 迁移脚本），schema 变更可回溯、可重放。
- **B2 数据完整性** — 报告问题：`records` 无 `NOT NULL`/`CHECK`/外键，存在必填为空、非法枚举等脏数据。原因：脏数据污染下游统计与导出。目标：关键字段加约束 + API 层严格校验。
- **B3 备份与恢复** — 报告问题：依赖人工备份，无定时备份/导出脚本。原因：人工易遗漏、故障时无据可恢复（叠加智能插座硬断电损库风险，更需制度化）。目标：服务器加定时备份任务 + 启动自检，备份策略可验证。
- **B4 敏感信息** — 报告问题：`STAMP_TOKEN` 硬编码在 `app.py`。原因：代码库一旦泄露，机器人接口可被滥用。目标：token 外置（环境变量 / secrets），定期轮换。

**C. API 与后端逻辑**
- **C1 输入校验** — 报告问题：自由文本（备注、客户编码）几乎无长度/格式限制。原因：极端输入可致前端渲染异常或库字段溢出。目标：统一长度/字符集/枚举过滤，前后端同步限制。
- **C2 错误处理** — 报告问题：部分路由未捕获异常导致 500 且无堆栈。原因：前端依赖错误信息会状态不一致。目标：统一错误处理器 + 仅服务端可见的 traceback 日志。
- **C3 权限控制** — 报告问题：无登录，仅前端 `user` 参数做粗粒度校验，关键操作（删除/导入/改配置）无防护。原因：任何能调接口的人都能增删记录。目标：关键操作加简易令牌 / 共享密钥 / IP 白名单，防误操作与外部滥用。
- **C4 幂等性** — 报告问题：`bump_version`/`sync_departure` 等有副作用，重复请求致版本号异常增长或意外改写。原因：前端卡死重复提交引发。目标：请求 ID 去重（短时间同 ID 不重复写入）+ 客户端保证单次提交。

**D. 前端与交互**（起点 = yxo_app 现有 `templates/static`，沿用 web 命名；前端技术栈选型待定）
- **D1 技术栈** — 报告问题：原生 JS，`app.js` 约 130KB，交互复杂后难维护。原因：看板/拖拽/批量编辑等需求增长会使原生代码失控。目标：引入轻量框架（如 Lit / Alpine）或至少模块化拆分（`utils.js`/`store.js`/`components.js`）。
- **D2 状态同步** — 报告问题：每 4 秒轮询 `/api/version`，频率固定。原因：用户多或网络差时产生无效流量、高并发响应慢。目标：WebSocket / SSE 推送，或至少轮询间隔可配置。
- **D3 错误容忍** — 报告问题：网络中断/超时处理弱，仅 `alert`/`toast`。原因：用户可能误以为操作成功。目标：统一请求封装（重试/提示/回滚 UI 状态）。
- **D4 离线能力** — 报告问题：完全依赖后端，离线无法查看/编辑。原因：仓库、货车等弱网场景无法工作。目标：Service Worker + IndexedDB 离线只读缓存，恢复连接自动同步。

**E. 部署、监控与工作流**
- **E1 日志与监控** — 报告问题：仅 `print`，无 logging 框架，无请求日志。原因：出问题时难以追踪。目标：标准 `logging`（INFO→`logs/app.log`，错误单独），记录关键操作（导入/删除/价格修改）与请求（IP/路由/耗时）。
- **E2 数据质量监控输出渠道** — 现状：`daily_health.py` 业务数据体检当前推企微。**目标：改为发邮件给毛骁洋**（HTML/表格，信息量大），不走企微纯文本——企微通知纯文本内容太少，承载不了脏数据清单。
- **E3 CI** — 报告问题：无 CI，依赖人工自测。原因：事故率高。目标：GitHub Actions 在 push `dev` 时跑 pytest + lint + 依赖漏洞检查，至少含「能否启动返回 200」烟雾测试。
- **E4 回滚** — 报告问题：`rollback.ps1` 未在仓库中。原因：回滚策略失效则恢复慢。目标：`rollback.ps1` 入库（仅服务器执行）+ `deploy.ps1` 明确展示备份位置与回滚步骤。
- **E5 启动与环境** — 报告问题：硬编码 `D:\YXO_DATA` 路径、依赖本机 Python venv。原因：换机/容器难跑。目标：路径改相对/环境变量/`config_local.py` 覆盖 + 提供示例模板。

**F. 安全与合规**
- **F1 身份认证** — 报告问题：无登录，`user` 参数可被冒用。原因：任何人可冒充任意用户操作。目标：共享密钥/令牌（`X-User-Token`），防外部恶意请求。
- **F2 传输安全** — 报告问题：接口走 HTTP，无强制 HTTPS。原因：直连内网端口（如 5011）数据明文。目标：nginx 强制 `X-Forwarded-Proto https` + Flask secure cookie，内网推行 HTTPS（自签证书）。
- **F3–F5 保持良好**（SQL 注入已参数化、CSRF/XSS 由 Jinja2 自动转义覆盖、敏感信息未入日志）：新代码延续该规范，杜绝 `{{ ... | safe }}` 与字符串拼接 SQL。

> 报告非代码类即时行动（确认备份完整性 / 导入前 dry-run / 观察协同延迟 / 记录异常现象 / 定期查数据异常）属运维习惯，不纳入代码改造，但落地后由 E1 日志与 E2 邮件监控兜底。

## 5. 旧代码避坑要点（仅参考，不纳入新代码）

- 分支名禁用斜杠（`feature/xxx` 是 8/5 `.git` 损坏根因）→ 用连字符 `feature-xxx`。
- 飞书凭据不要硬编码 → 走 secrets 外置。
- 生产库不要与代码混库 → 数据层独立。
- 不要靠 SMB / ZeroTier 传任务（单点故障）→ 走 GitHub `tasks/`。
- 手写 LLM 调用（WeComBot NLP 等）不要裸奔客户 PII → 经 gate 脱敏 + 设超时 fallback；agent 自身与 opencode 内置模型由框架管，不在此列。
